# Guard: Clauses

Clauses are the foundational underpinning of Guard rules. Clauses are boolean statements which evaluate to a `true` (`PASS`)/ `false` (`FAIL`) and take the following format:

```
  <query> <operator> [query|value literal]
```

You must specify a `query` and an `operator` in the clause section:

- `query` in its most simple form is a decimal dot (`.`) formatted expressions written to traverse hierarchical data. More information on this section of the clause can be found in the [Guard: Query and Filtering](QUERY_AND_FILTERING.md) document.

- `operator` can use _unary_ or _binary_ operators. Both of these operators will be discussed in-depth later in this document:

  - _Unary Operators:_ `exists`, `empty`, `is_string`, `is_list`, `is_struct`, `is_bool`, `is_int`, `is_float`, `not(!)`
  - _Binary Operators:_ `==`, `!=`, `>`, `>=`, `<`, `<=`, `IN`

The `query|value literal` section of the clause is optional:

- `query|value literal` the third section of a clause is needed when a binary operator is used. It can be a `query` as defined above or it can be any supported value literal like `string`, `integer(64)`, etc.

Below are some examples for clauses:

- Clauses using unary operator:

```
# The collection TcpBlockedPorts cannot be empty
InputParameters.TcpBlockedPorts not empty
```

```
# ExecutionRoleArn must be a string
Properties.ExecutionRoleArn is_string
```

- Clauses using binary operator:

```
# BucketName must not contain the string "encrypt" irrespective of casing
Properties.BucketName != /(?i)encrypted/
```

```
# ReadCapacityUnits must be less than or equal to 5000
Properties.ProvisionedThroughput.ReadCapacityUnits <= 5000
```

## Operators

Let us look at Guard supported `operators` in-depth. Information on each operator will be accompanied by examples based on the following example CloudFormation template to help you understand the various operators. All examples in this section will be based on the following template:

```yaml
# Template-1
Resources:
  S3Bucket:
    Type: "AWS::S3::Bucket"
    Properties:
      BucketName: "MyServiceS3Bucket"
      BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault:
              SSEAlgorithm: "aws:kms"
              KMSMasterKeyID: "arn:aws:kms:us-east-1:123456789:key/056ea50b-1013-3907-8617-c93e474e400"
      Tags:
        - Key: "stage"
          Value: "prod"
        - Key: "service"
          Value: "myService"
```

### Unary Operators

#### `empty` and `exists` operators

Guard introduces `empty` and `exists` operators to assist authors verify states of the `query` in a clause. You can use the `not(!)` operator with both these operators to check the inverse state.

`empty`- Checks if a collection is empty. It can also be used to check if a query has values in a hierarchical data as all queries result in a collection, more about queries is mentioned in the [Guard: Query and Filtering](QUERY_AND_FILTERING.md) document.

```
# Checks if the template has resources defined
Resources !empty
```

```
# Checks if one or more tags defined
Resources.S3Bucket.Properties.Tags !empty
```

The above two clauses will `PASS` for the example template.

- The first clause checks to see if the template has resources defined under `Resources` , and the template has one resource with `S3Bucket` as the logical resource ID.
- The second clause checks to see if one or more tags are defined in `S3Bucket`. It has two tags defined under `Tags`.

`empty` can be used to check if string value queries have an empty string (`""`) defined.

On a value that cannot be empty — a number or a boolean — `empty` has no answer, so the clause fails and the report names the path and the operator. `not empty` fails as well: an integer is not empty, but reporting it as non-empty would accept a clause that never checked anything. Only the clause fails; the rest of the rules in the file are still evaluated and reported.

A `null` value is empty. `Properties.Encryption empty` passes when the template sets `Encryption: null`, and `not empty` fails on it, the same answers a key that is absent gets below. The key is still present, so `exists` passes on the same value. As a condition, `when Properties.Tags !empty` over a bare `Tags:` (which YAML reads as null) means the rule does not apply, exactly as it does when `Tags` is missing; it no longer fails the rule because the condition could not be answered.

`exists` - Checks if each occurrence of the query exists.

```
# Checks if BucketEncryption is defined
Resources.S3Bucket.Properties.BucketEncryption exists
```

The above clause will `PASS` for the example template as `BucketEncryption` is defined for `S3Bucket`.

> **IMPORTANT**: `empty` and `not exists` checks evaluate to true for missing property keys when traversing the input data. E.g. if we check `Resources.S3Bucket.Properties.Tags empty` if `Properties` was not present in the template for S3Bucket, then `empty` evaluates to true.

#### Array indexes

An index selects one element: `Items[0]` is the first and `Items[-1]` is the last, with `Items[-2]` the one before it. An index that names no element — past the end in either direction, or too large to be an offset at all — does not resolve, and the clause reports that rather than selecting a different element.

```
# the last tag, whatever the length of the list
Resources.MyBucket.Properties.Tags[-1].Key == "Owner"
```

#### `is_string`, `is_list`, `is_bool`, `is_int`, `is_float` and `is_struct` operators

`is_string` - Checks if each occurrence of the query is of `string` type.

```
# Checks if BucketName is defined as a string
Resources.S3Bucket.Properties.BucketName is_string
```

`is_bool` - Checks if each occurrence of the query is of `bool` type.

```
# Checks if ObjectLockEnabled is defined as a bool
Resources.S3Bucket.Properties.ObjectLockEnabled is_bool
```

`is_int` - Checks if each occurrence of the query is of `int` type.

```
# Checks if Port is defined as an int
Resources.ELBListener.Properties.Port is_int
```

`is_float` - Checks if each occurrence of the query is of `float` type.

```
# Checks if CompletionWindowMinutes is defined as a float
Resources.BackupPlan.Properties.BackupPlan.BackupPlanRule { CompletionWindowMinutes is_float  }
```

`is_list` - Checks if each occurrence of the query is of `list` type.

```
# Checks if Tags is defined as a list
Resources.S3Bucket.Properties.Tags is_list
```

`is_struct` - Checks if each occurrence of the query is a structured data.

```
# Checks if BucketEncryption is defined as a structured data
Resources.S3Bucket.Properties.BucketEncryption is_struct
```

`is_null` - Checks if each occurrence of the query is of `null` type.

```
# Checks if Resources.S3Bucket.Properties is null
Resources.S3Bucket is_null
```

All the above example clauses will `PASS` for the example template. You can use the `not(!)` operator with the above operators to check the inverse state.

### Binary Operators

Below are binary operators supported in Guard. The left-hand side (LHS) to the operator as mentioned above must always be a query and the right-hand side (RHS) can be a query or a value literal:

```
  ==    Equal
  !=    Not Equal
  >     Greater Than
  >=    Greater Than Or Equal To
  <     Less Than
  <=    Less Than Or Equal To
  IN    In a list of form [x, y, z]
```

A value literal can be from any of the following supported categories,

- all primitives `string`, `integer(64)`, `float(64)`, `bool`, `char`, `regex`
- a specialized range type for expressing `integer`, `float`, `char` ranges, expressed as,
  - `r[<lower_limit>, <upper_limit>]`, which translates to any value `k` that satisfies the following expression: `lower_limit` <= k <= `upper_limit`
  - `r[<lower_limit>, <upper_limit>)`, which translates to any value `k` that satisfies the following expression: `lower_limit` <= k < `upper_limit`
  - `r(<lower_limit>, <upper_limit>]`, which translates to any value `k` that satisfies the following expression: `lower_limit` < k <= `upper_limit`
  - `r(<lower_limit>, <upper_limit>)`, which translates to any value `k` that satisfies the following expression: `lower_limit` < k < `upper_limit`
- associative arrays (a.k.a map) for nested key value structured data like:

```
{ "my-map": { "nested-maps": [ { "key": 10, "value": 20 } ] } }
```

- arrays of primitive/associative array types

Comparisons are between values of the same kind, with one exception: `integer` and `float` compare against each other as numbers. That includes range membership, so `Size IN r[5.0, 100.0]` holds for a `Size` of `50` and `Size IN r[5, 100]` holds for a `Size` of `50.5`. `Size > 10` holds for a `Size` of `50.5`, and `Size == 50` holds for a `Size` of `50.0`. Earlier versions treated the two as different types and reported that they could not be compared, which failed the clause. Comparing across kinds that are not both numeric, a `string` against an `integer`, say, still cannot be decided, and the clause fails rather than guessing.

`null` is the other exception, for equality only. A `null` is equal to `null` and to no string, number, boolean, map or list, so `KmsKeyId != null` holds when `KmsKeyId` is set to anything else and `KmsKeyId == null` holds only when it is `null`. The same applies with the `null` in the template: a property written as `KmsKeyId: null` fails `KmsKeyId == "arn:..."` and passes `KmsKeyId != "arn:..."`, and it is in no list, so `KmsKeyId IN [...]` fails and `KmsKeyId NOT IN [...]` passes. A denylist is therefore satisfied by a property that is present and `null`; a rule that also needs the property set says so with `exists` or `!= null`. In short: a property that is present and `null` compared with `!=` to a non-null literal passes, and compared with `==` fails; a property that is absent still fails both, because a missing key is a retrieval failure rather than a `null`; and no notice is printed for either, since this is a change in what the comparison means rather than a deprecation. Earlier versions reported a `null` against any other kind as not comparable, which failed the clause in both polarities, so `!= null` could never hold. Ordering against `null` (`>`, `>=`, `<`, `<=`) and a `null` against a range or a regular expression still cannot be decided, and those clauses fail.

The distinction matters most inside a `when` condition. A condition that cannot be decided does not pass, and a rule whose condition does not pass is reported as not applicable, so the block it guards is never checked. A rule written as

```
rule large_volumes_are_encrypted when Resources.*[ Type == 'AWS::EC2::Volume' ].Properties.Size > 10 {
    Resources.*[ Type == 'AWS::EC2::Volume' ].Properties.Encrypted == true
}
```

now applies to a template whose `Size` is `50.5` as it always did to one whose `Size` is `50`.

A comparison across kinds that are not both numeric is a sharper problem in the same place, and one to be aware of when writing conditions. CloudFormation templates frequently carry numbers as strings, `Size: "50"` rather than `Size: 50`, and a string cannot be compared against `10`. The condition cannot be decided, so it does not pass, so the rule is reported as not applicable and the block it guards is never checked. The run exits `0`, exactly as it would for a rule that genuinely did not apply.

Guard reports which of the two happened. A rule skipped because a condition could not be decided says so, naming the operand kinds:

```
SKIP rules
large_volumes_encrypted_gate.guard/large_volumes_are_encrypted    SKIP
  large_volumes_are_encrypted: the rule did not apply because one of its conditions could not be decided: PathAwareValues are not comparable String, int
```

The same explanation appears under `not_applicable_reasons` in `--output-format json` and `yaml`.

A collection that is present and empty on the LEFT-hand side is a retrieval error, like a missing key, and a comparison over it fails on every binary operator in both polarities: `==`, `!=`, `<`, `<=`, `>`, `>=`, `IN` and `NOT IN`. `Ports IN [80, 443]` over a `Ports` of `[]` fails naming the empty collection; an empty list is not read as a subset of the set. A document `[]` on the RIGHT-hand side is a present value the left-hand values are compared against (`NOT IN []` passes each one), so it is an absence only for a left-hand value no comparison accepted; the behavior-change entry on a marker among a comparison's right-hand values, below, states that side. This is about collections the document resolved to: a `[]` written in the rule, inline or bound through `let`, is a value the author wrote and compares as one: a scalar compared with `==` or `!=` to a list literal is incomparable, in both polarities, so `Mode == []` and `Mode != []` over a string both fail on the kinds as `Mode == [1]` and `Mode != [1]` do; `[] == []` holds; and under `IN` a list literal reads element-wise whatever the right side's kind, so `[] IN [80, 443]` and `[] IN 80` are both false and `[] NOT IN [80, 443]` and `[] NOT IN 80` both true. In a `when` condition the same comparison is not satisfied, as it is not by a missing key, so the rule is reported not applicable and the reason names the empty collection; in a query filter it deselects the entry. Guard the comparison with `<query> !empty` as a sibling condition where an empty collection is expected and the body should still be checked.

A rule skipped because its condition was decided and simply not met prints no such line, so the message appears only where something needs attention. If you see it, the fix is in the rule or the input rather than in Guard: compare against a value of the same kind, or guard the clause so the mismatch is explicit.

Below are a couple of examples of clauses using binary operators:

- Based on the Template-1 example template:

```
# Checks if BucketName does not contain the string "encrypt" irrespective of casing
Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
```

- Consider the following CloudFormation template:

```yaml
# Template-2
Resources:
  NewVolume:
    Type: AWS::EC2::Volume
    Properties:
      Size: 100
      VolumeType: io1
      Iops: 100
      AvailabilityZone:
        Fn::Select:
          - 0
          - Fn::GetAZs: us-east-1
      Tags:
        - Key: environment
          Value: test
    DeletionPolicy: Snapshot
```

Below are a few Guard clauses based on the above template:

```
# Checks Size of the EC2 volume is within a specific range, 50<= Size <= 200
Resources.NewVolume.Properties.Size IN r[50,200]
```

```
# Checks VolumeType is one of io1, io2 or gp3
Resources.NewVolume.Properties.VolumeType IN [ 'io1','io2','gp3' ]
```

> While these examples illustrate using `S3Bucket`, `NewVolume` in the query, often these are user defined and can be arbitrarily named in an IaC template. To write a rule that is generic and applies to all `AWS::S3::Bucket` resources defined in the template the most common form of query used is `Resources.*[ Type == ‘AWS::S3::Bucket’ ]` to select them. See [Guard: Query and Filtering](QUERY_AND_FILTERING.md) for details on usage and explore the examples directory.

> A filter `[ ... ]` directly after a part that names a collection (a key, `this`, or a `%variable` in a key's place) selects among that collection's entries; directly after a part that names one value (an index, an earlier filter, a `[ keys == ... ]` filter, or a wildcard-expanded member) it tests that value. So `Resources { this[ Type == 'AWS::S3::Bucket' ].Properties.Encrypted == true }` is the same check as `Resources[ Type == 'AWS::S3::Bucket' ].Properties.Encrypted == true` once the block has a value to run over: a block over a null or empty population (a bare `Resources:`, `Resources: {}`, or `Resources: []` under `this[*]`) reads a selection in its body, `this[ f ]`, `this.*[ f ]`, `this[*][ f ]` or `this[*].K[ f ]`, as the empty selection, so it is not applicable as the plain spelling is. The block spelling is also an existence check on `Resources` itself, so over a template with no `Resources` key it fails at its query where the plain spelling is not applicable. A filter predicate written inside such a block tests its entry, not the population: `Resources { this[ this[ Type == 'X' ] !exists ] exists }` reads an entry that is `null` or `{}` exactly as `Resources[ this[ Type == 'X' ] !exists ] exists` does. A bare `this` hands the population on: a block nested in the block, `Resources { this { this[ Type == 'X' ] exists } }`, and a parameterized rule called with it, `Resources { check(this) }` for `rule check(p) { %p[ Type == 'X' ].Properties.Encrypted == true }`, read a bare `Resources:` as `Resources { this[ Type == 'X' ] exists }` and `check(Resources)` do, not applicable rather than failing. The same holds for a wildcard, a key and then a filter at the population: `Resources[*].Properties.Tags[ Key == 'Env' ] exists` and `Statement[*].Condition[ keys == 'x' ] exists` are not applicable over `{}`, over a bare `Resources:` or `Statement:`, over `Resources: {}` and over `Resources: []` alike, where over the bare key and over the empty map they used to fail on the key below it, and their `!exists` over the same two used to pass, reading the key as absent, and is not applicable as well, so a `when` gate written on it that used to open its block leaves it unopened; below the population, `Properties.Statement[*].Condition[ keys == 'x' ]` over a bare `Statement:` still fails on the key `Condition`. Through an alias of the population, `let r = Resources` then `%r.B.Properties.Tags[ Key == 'Env' ] exists`, a template with no `Resources` key fails on the key `B`, as the spelling without the alias does, where the alias used to be not applicable. `Rules[0][ Action == 'allow' ]` is the first rule when its action is `allow`. Inside a block over members, `Rules[*] { this[ Action == 'allow' ] exists }` selects among each rule's own entries, not among the rules; when such a filter selects nothing and its predicate names a key of the member itself, the clause is refused and fails in both polarities. The refusal leads with the spelling that is right where the clause sits, `{ Key == value }` in the block, so `Rules[*] { Action == 'allow' }`, and then names the two spellings that read one member and a list of them alike from outside the block, `X[*] { Key == value }` and `X[*].Key == value`, where `X` is the query that named the member (`Rules` here) and `Key` the key the predicate read (a key-spelled filter, `Rules[ Action == 'allow' ] exists`, is not named: over a `Rules` written as one object it is the same misreading). The same holds when the one map is named by its key: `Resources.B1[ Type == 'AWS::S3::Bucket' ] exists` selects among `B1`'s own entries, and when the filter keeps none of them while `Type` is a key of `B1` and of none of its map-valued entries, it is refused the same way; the predicate is read with a leading `this.` looked through here too, so `Resources.B1[ this.Type == 'AWS::S3::Bucket' ] exists` is refused as the spelling without `this.` is, where it used to be left to evaluate and was not applicable at exit 0; the refusal reads "The filter selected nothing among the map's own entries. `Key` is `Type`, a key of the map itself. Write `X[*] { Key == value }` or `X[*].Key == value`, where `X` is `Resources.B1`, at path /Resources/B1." (the member spellings, `X.*.Key` and `X.* { Key == value }`, are offered as one sentence between the definition of `X` and the path, "For each member's own `Key`: `X.*.Key` or `X.* { Key == value }`.", only when the entry under the key is itself a plain member map, a member named like the key; `B1`'s `Type` is a string, so no member holds it and the sentence is left out, as it is over an intrinsic call such as `Effect: !If [...]` or an empty map such as `B: {}`). Both spellings read one map and a list of them alike, and `X` is the query the author wrote before the filter, so the spellings test the map in hand, `Resources.B1[*] { Type == 'AWS::S3::Bucket' }` or `Resources.B1[*].Type == 'AWS::S3::Bucket'`, and read a `Statement` named the same way whether it is written as one object or as a list; after a key the refusal does not lead with the in-block spelling `Resources.B1 { Type == 'AWS::S3::Bucket' }`, which reads nothing over a list. The spellings carry the placeholders `X` and `Key`, and the query and the key are printed once, so that the console summary and the JSON and YAML reports print the key, both spellings, the definition of `X` and, where a member is named like the key, the member sentence, up to 4096 characters, with a marker where the console cut the explanation there (`-o json` carries the whole text), and the path last; the path, like every part a refusal takes from the template (an entry's or a key's name), is bounded at 256 characters: a name longer than that is cut at its end with a marker naming how much was cut, and a path is cut in its MIDDLE, keeping the top of the document, a marker, its leaf segments and its `[L:x,C:y]` location (so a long refusal path reads `/Resources/RRRR...[44 more characters cut].../Properties/Tags[L:3,C:9]`), and a part only a few characters over the bound is left whole, since the marker would make it longer; so no template decides the line's length and the sentence around it stays whole. The two collection spellings are the ones that read a map and a list of such maps the same way, which matters where a property may be written as either: an IAM `Statement` written as one object, `PolicyDocument.Statement[ Effect == 'Allow' Action == '*' ] empty`, used to pass by accident and is now refused, and `Statement[*] { Effect == 'Allow' Action != '*' }` or `Statement[*].Action != '*'` reads both shapes. A collection one of whose entries happens to be named like the predicate's key (a parameter called `Type` under `Parameters`) is still a selection among members and is not refused, since its members each carry the key.

Each pair reports at its entry's own path (`/Resources/Fn/Properties/Tags/Env`), the node the template has.
The per-value bookkeeping a comparison keeps beside a refused value (which left-hand values a resolved entry decided) keys a value by its identity, never by its path, so two values that report at one path, a pair's synthetic `Key` node and a sibling key spelled with a slash among them, are two values to it; the reporters tell them apart by location.
One notice per filter site whose twin kept a pair names the filter as written, the map's path and keys (never a value: a `Variables[*][ Key == /PASSWORD/ ]` filter would otherwise write the secret to the error stream) and `<X>.<key>` as the way to read the map itself, for the first map decided at that site and standing for every other map the filter meets (no per-map count). A verdict that moves is never silent: the notice is also written, once per site, where the twin kept NO pair of a map the one-object reading had kept (`[ Value empty ] empty` or `[ Key !exists ] empty` over `{ Env: dev }`, which the object held by the absence of a pair field and the twin lets pass), its text saying the twin kept no pair; a filter whose twin and one-object reading both keep nothing of every map it meets (`[ Key == 'Env' ] exists` over `{ Team: platform }`) is not announced.
A predicate that is not pair-shaped (a key the pair has not, `Sid`, `Action`, `Principal`; a comparison against a document query or a function; a `when`, a block or a rule call) and a map with a non-scalar entry keep the one-object reading below; a `%name` bound by a query (a query-bound `let`, a parameter given a query, an alias of either) is a literal candidate to the pair shape, so the predicate is pair-shaped with it and the twin reads what the name resolves to: one scalar literal (a string, a number, a boolean, a null) reads as the literal spelling, and anything else (a list, a map, several values, none, an error) leaves the twin unable to read the name, so the selection is refused when read bare, the name and the kind of any error named, fail closed (`[ Key !exists or Key IN %names ]` with a list-bound `%names` is refused over `{ Env: dev }` and over `{ Team: x }` alike, where its list twin decides each element); a `%name` that holds no literal and no query (a capture, a key a block merged up, a function call) is refused the same way when the selection is read bare (the name's value is not fixed at the filter), fail closed; a negated comparison with no key head (`[ this != 'x' ]`, `[ %v != 'x' ]` with `let v = 'y'`) is read over the twin's pair as the evaluator reads a list element (a pair compared with a string is not comparable and is excluded, a `%name` is compared as it stands), so `[ this != 'x' ] empty` passes and `[ %v != 'x' ] empty` fails over `{ Env: dev }` as over its list twin, with no refusal; and "read bare" means every reader of the selection: a unary clause (`%env exists`), either operand of a comparison (`%env == 'x'`, `%x == %env`, a `when %x == %env` gate) and a function's argument (`count(%env)`); inside a filter predicate the refused operand arrives as a marker among the comparison's values, and a value the document holds compared against it is undecided, so `[ Properties.Held == %env ]` fails closed as `[ %env == Properties.Held ]` does. An ABSENT operand beside the marker is decided, under every comparator and in both polarities: the absence fails its comparison whatever the refused selection holds, so `[ Properties.Missing == %env ]` and `[ %env == Properties.Missing ]` deselect an entry that lacks `Missing`, `when Properties.Missing == %env` is not applicable, and `[ Tags IN %env ]` over `Tags: []` deselects as it does over a missing `Tags`; the refusal is still reported, its reason written into the record of the absent value beside the decided comparison (the marker's own record, when the marker is the left operand) and registered as a refusal, so a mistake behind `%env` is never silent over a template whose every entry lacks the property.

#### `IN` against a query

The RHS of `IN` and `NOT IN` can be a query instead of a literal. The rule: a query that **enumerated** a collection while it was resolved (`[*]` or `.*` over a collection, a filter, an interpolated key whose variable enumerated or holds a list of keys, or a variable whose own query did any of those) is the set of its results, and `IN` is membership in that set, exactly as it is in the list literal the results would spell out. A query that **named** one value compares against that value: a list is membership, a string is containment of the LHS string in it. The shape is what the retrieval did, so `Types[*]` over a one-entry list and `Types[0]` are different shapes with the same value.

A scalar on the LHS is a member of the entries with list-valued results flattened one level, whatever part of the query enumerated: a scalar is never a member of a list, so the lists an enumeration hands back can only be lists of candidates for it. A list on the LHS is a subset question: of one result at a time when an earlier part enumerated, of the whole entries when the last part did, exactly as against the written-out list of lists. A value no string entry can be compared with (an int or a `!Ref` map against strings) is refused, and the clause fails in both polarities, as it did before; a value some entry can be compared with is decided, and a value against entries of another non-string kind is a miss, as it is against the written-out list. Under `some`, the verdict is per LHS value in every spelling.

The two polarities for a list on the LHS against list-valued results are deliberately asymmetric and both fail-closed, whichever part enumerated: `IN` is not widened to the pool of all results, and `NOT IN` is not opened by a list that shares one element with a denied one. A result the query cannot resolve, such as `Parameters.*.AllowedValues` over a parameter that has no `AllowedValues`, fails the clause as an unresolved RHS fails any `IN`.

Two sites compare key by key rather than as a set: a map-key filter (`Resources[ keys IN %allowed ]`) and a capture read bare as the RHS (`X IN %name` after `Resources[ name | ... ]`). In a map-key filter a string key is equal to a string element, never contained in it: `[ keys IN ['Environment'] ]` and `[ keys IN 'Environment' ]` both select the key `Environment` and not `Env`. Earlier releases read a bare string, a `let`-bound string or an enumerated string on the right as text the key could be contained in, and a key whose selection moves that way draws a `DEPRECATION` notice; see [KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 13. A negated map-key filter (`NOT IN`, or `!=` over two or more values) selects a key that differs from every right-hand value, where earlier releases selected one that differed from any; a key equal to one of two or more enumerated values, which used to be selected and checked and is left out now (`Resources[ keys NOT IN %exempt ]` over an exemption list of two names, FAIL to PASS or to SKIP), draws its own `DEPRECATION` notice, under the same item. A key or a right-hand value either notice quotes is written as document text is everywhere a notice quotes it: a control, bidi or zero-width character as its Rust escape (`\t`, `\u{200b}`) and a backslash doubled (`a\\b` for the key `a\b`), so the notice stays one line and two keys that differ only in such a character print apart. A map-key filter whose RHS is the empty set is decided by polarity. The empty set is a collection with nothing in it, reached by an enumeration (`keys NOT IN %exempt` with `let exempt = Mappings.Exempt.Names[*]` or `Mappings.Exempt.Names.*` over `Names: []` or `Names: {}`), a key holding null (a bare `Names:` in YAML), or the empty list literal (`let exempt = []`). No key is in it, so `==` and `IN` select no key and the rule reports SKIP; every key is outside it, so `!=` and `NOT IN` select every key and the rule checks all of them. An empty exemption list exempts nothing, where a filter that selected none checked nothing at exit 0. Both engines read it this way. An RHS the key filter cannot resolve fails the filter closed under every comparator, `==` and `!=` included, with a reason naming the path the retrieval stopped at: the keys it would select cannot be decided, so the rule reports a failure rather than selecting none and passing. A right-hand query that is itself refused on the data, `M[ keys == Tags[ Key == 'Env' ].Value ]` or `M[ keys == to_upper(Tags[ Key == 'Env' ].Value) ]` where `Tags` holds a string, fails the filter closed the same way: the map is recorded as undecidable with the refusal as its reason, the clause reads that record as it reads every undecidable map (a rule over the one refused map fails closed in either polarity; under `some` over several maps a sibling whose own selection passes settles the clause past it, so the rule passes; a `when` gate over several maps whose operator is a comparison is settled by a sibling, a decided failure under `all` making the rule not applicable and a pass under `some` opening the block, while a gate under `exists`, `!exists`, `empty` or `!empty` raises on the undecidable map and fails the rule closed whatever the siblings say), and the query goes on to the next map; a capture on the filter holds the marker, so a clause reading it fails closed with the reason. It used to leave the clause with no check recorded and the line "Clause could not be evaluated against the incoming context ... when handling clause, bailing" in its place, failing the clause closed whatever the siblings said, where the same query inside a filter predicate was recorded per map; the `some` and `when` readings over several maps are the two verdicts that moved with the record. The failure follows the selection wherever it is read as a clause's own query: a `when` gate over it fails its rule rather than reporting it not applicable, a comparison on either side fails rather than reading the selection as an absent property, and a `some` binding keeps it so that `empty` over the binding fails; the same holds for a comparison the engine could not finish, a regex out of backtracking budget. #### Filtering through a variable

A filter written after a variable, `%v[ ... ]`, walks the entries of the value `v` holds and keeps the entries whose values satisfy the predicate. This is the same reading the literal path has: `let r = Resources` then `%r[ Type == 'AWS::S3::Bucket' ]` selects what `Resources[ Type == 'AWS::S3::Bucket' ]` selects.

The reader puts a `[*]` after every `%variable` root that has parts after it. What that `[*]` does depends on what the variable holds.

Over a list, the variable enumerates it: `%r.K` over a list is `Resources[*].K`, with one exception, a filter written directly after the variable over an empty list below the top level, which reads as the literal filter (two paragraphs down). Over `Resources: []` with a filter further along, `%r.B.Properties.Tags[ Key == 'Env' ] exists` is the empty population and is not applicable, as `Resources[*].B.Properties.Tags[ Key == 'Env' ] exists` is; over one element the two spellings pass or are not applicable together; and over `Resources: []` with no filter ahead, `%r.B.Properties.Tags exists` and `Resources[*].B.Properties.Tags exists` both fail on the empty enumeration. The key spelling `Resources.B.Properties.Tags[ Key == 'Env' ] exists` is a different query: a list has no key `B`, so it fails on the key over any list, empty or not. A Terraform plan reads the same way through its alias: `let rc = resource_changes` then `%rc[ type == 'aws_s3_bucket' ].change.after.acl == 'private'` is not applicable over `resource_changes: []`, over a plan with no `resource_changes` key and over a plan whose only change is an instance, as the literal filter spelling is, and passes over a private bucket and fails over a public one as it does; `%rc.change.after.acl == 'private'` over the empty list fails as `resource_changes[*].change.after.acl == 'private'` does.

Over a map, a null or an absent key, the `[*]` the reader adds is not an authored `[*]`: it passes the value on unchanged, so `%r.B` is `Resources.B`, and the alias and key spellings agree. Over `Resources: {}`, a bare `Resources:` and a template with no `Resources` both fail on the key `B`; over a template whose `Resources` map holds `B` with the tag, both pass. The authored `Resources[*].B.Properties.Tags[ Key == 'Env' ] exists` agrees with them over a map that holds `B`, passing, but it reads `Resources: {}`, a bare `Resources:` and a template with no `Resources` as an empty population with a filter ahead and is not applicable there, where the alias and the key read fail on the key.

Below the top level the `[*]` the reader adds after a variable reads an empty list under a filter written directly after the variable as the literal filter does: `let cs = spec.template.spec.containers` then `%cs[ name == 'app' ] exists` over `containers: []` is not applicable, in both polarities and as a `when` gate, as the literal `spec.template.spec.containers[ name == 'app' ] exists` is, where the authored `containers[*][ name == 'app' ] exists` fails on the empty enumeration; `%cs.name` and `%cs[*][ name == 'app' ]` over the same list fail as `containers[*].name` and the authored wildcard do; over a populated list, a missing key or a null the three spellings of the filter, the alias `%cs[ name == 'app' ]`, the literal `containers[ name == 'app' ]` and the authored `containers[*][ name == 'app' ]`, agree (`docs/KNOWN_ISSUES.md`, item 6). The slot reads the list the variable holds however it came to hold it: a let-chain (`let all = spec.template.spec.containers` then `let cs = %all`), a parameterized rule's parameter bound to the list at the call, a key read after the filter (`%cs[ name == 'app' ].image exists`) and a list one level down (`let cs = spec.containers`) read the empty list as the literal filter does. An empty MAP under the same slot reads the same way: `let cs = Resources.X.Properties.Containers` then `%cs[ name == 'app' ] exists` over `Containers: {}` is not applicable in both polarities and as a `when` gate, as the literal `Resources.X.Properties.Containers[ name == 'app' ] exists` is, where it used to fail on the empty enumeration under `exists` and pass on it under `!exists`; the authored `Containers[*][ name == 'app' ]`, `%cs.name`, `%cs[*][ name == 'app' ]` and `%cs.*[ name == 'app' ]` over the empty map keep the enumeration's failure, and over a map with members, a missing key and under a map-key filter (`%cs[ keys == 'x' ]`) the alias and the literal agree as they did. A map-key filter directly after the variable is the slot's own reading, not the literal's: over a populated list `%cs[ keys == 'x' ]` reads as `containers[*][ keys == 'x' ]`, the key filter run over each element, selecting the elements that hold `x` and nothing over a list of maps that lack it; over the empty list it is not applicable (`exists` not applicable, `empty` passes), where both literal spellings fail: the authored `containers[*][ keys == 'x' ]` on the empty enumeration, and `containers[ keys == 'x' ]`, which reads the list as the map to filter, on a type error at any length ("Map Filter for keys was not a struct array"), so that literal's `exists` fails and its `empty` passes over a list. Over a map of containers the slot hands the map on and the two spellings agree.

A parameterized rule's parameter is a variable of the rule, bound at each call, and `%p` anywhere in the rule reads it. A filter capture in the rule's own `when` condition written under a parameter's name, `rule check(p) when Resources[ p | Type exists ] !empty { %p[ Statement exists ] !empty }`, could never be read, so the file is refused when it is loaded, as a name that is both assigned and declared as a filter capture in one scope is; rename the capture.

Inside a block, a `%name` is read in one order by every clause of the block: a key a nested block handed up (`Opts { Allowed[ t | On == true ] !empty }` hands `t` up to the block around it) comes first, then the block's literal `let` of that name, then the enclosing scopes; so a merged key shadows a block's literal `let t = 'x'`, the predicate that reads `%t` compares against the handed-up key, and the shadowing notice asks the author to rename one of the two. (A block that both declares a `let` and captures the same name in its own filter is refused when the file is loaded, so a capture never shadows a `let`.) The rows are pinned by eval_tests.rs:a_merged_key_shadowing_a_blocks_let_writes_no_quiet_record_at_either_site.

When the variable holds a single map, the entries are that map's own values, not the map. The predicate is tested against each entry instead. A positive predicate such as `Metadata."AWS::CloudFormation::Authentication" exists` holds on an entry only when that entry is itself a map carrying that key, as a `Wrapper` entry whose own `Metadata` map held an `AWS::CloudFormation::Authentication` block would, and a scalar entry such as `Type` is passed over, neither selected nor reported. In the example below, the positive predicate `Metadata."AWS::CloudFormation::Authentication" exists` holds on none:

```
# Resources.WebServer is one resource, an instance whose Metadata carries an
# AWS::CloudFormation::Authentication block
let m = Resources.WebServer

# Walks the entries of that resource. Its Metadata and Properties maps have no Metadata
# key, so the predicate rejects them; its Type string is a scalar entry, passed over.
# Nothing is selected in the resource's place.
let auth = %m[ Metadata."AWS::CloudFormation::Authentication" exists ]
```

By contrast, an absence predicate on the same resource, `%m[ Properties.Tags !exists ]` or `%m[ Properties.Tags empty ]`, holds on the map entries that lack the key: it selects the resource's `Metadata` and `Properties` maps in the resource's place, and passes the `Type` string over, neither selected nor reported. Where the key spelling passed a scalar over under a predicate that holds on the map read as one object, it is refused in both polarities, whether it kept nothing, with or without a map-valued entry tested and rejected, or kept a map-valued entry in the map's place: `spec[ securityContext !exists ]` over a `spec` holding `replicas: 3` alone, `Cfg[ Owner !exists ]` over `Cfg: { Mode: fast, A: { Owner: o }, B: { Owner: p } }`, whose sub-maps carry the key and are rejected while `Mode` is passed over, and `Statement[ Condition !exists ]` over a statement written as one object whose `Principal` is a map, which kept the principal where the statement should be, all exit 19, since the scalar passed over is the one candidate the absence check never read, and a kept field of one object is not the object. The refusal defines `X` first and then names the remedy in placeholder spellings: `X[*][ ... ]`, which reads the map as one object and selects it by the absence, as the list form selects its one member (`spec[*][ securityContext !exists ]`), and, where a map-valued entry was tested and rejected or kept, `X.*[ ... ]` for the members and `X.Key !exists` for the map itself (`Cfg.*[ Owner !exists ]` passes `empty` over the two sub-maps, both carrying `Owner`; `Cfg.Owner !exists` asks the map the question the author wrote; `Cfg[*][ Owner !exists ]` is not named there, since it reads the mixed map as one object and is refused again); whether a member was tested is read from the walk, so a directive passed over beside the scalar, or a null the predicate dropped, leaves the one-remedy text; inside a block over the member (`Cfg { this[ ... ] }`) the members reading is `this.*[ ... ]` and the member is asked with `Key !exists` as a clause over it. A selection of nothing in the key spelling's place would pass `empty` and skip a `when` gate that those spellings fail. The refusal is a disagreement test: the predicate is asked once, quietly, of the map as one object, and a predicate that does not hold there is not refused, since the selection of nothing is then the answer every spelling gives: `Owner == 'x'`, which no scalar satisfied; `Enabled == true Owner !exists` over a map that lacks `Enabled`, in either order of the clauses; `Owner !exists` over a map that holds `Owner` itself beside a member that holds it too. The probe reads the predicate as `X[*][ ... ]` would read it, fallback and errors included: a key filter's function argument the map lacks is read from the scope beside the map, so `Cfg[ Owner !exists  this[ keys == to_upper(Env) ] !empty ] empty` over `Cfg: { Mode: fast, PROD: 1 }` with `Env` at the document root is refused at exit 19 over `Env: prod`, where the `[*]` reading holds on `PROD` and fails `empty`, and passes unrefused over `Env: dev`, where both readings fail the key filter and pass `empty` (it used to pass unrefused over `prod` too, the readings disagreeing unseen); and an error the probe meets is the filter's own, so `Cfg[ Owner !exists  this[ Owner !exists ] !empty ] empty` over the same map raises the nested refusal the `[*]` spelling raises (`` `X` is the member the block is over `` ... at exit 19) rather than the pass-over remedy, unless a conjunct beside it fails for real (`Kind == 'k'` over a map without `Kind`), when `empty` passes under both spellings; a rules-file mistake inside the predicate (`parse_int('abc')`) stops the run at exit 5 under both. A query-bound `%variable` is resolved quietly by the probe; only a name no scope binds, a rule reference or a call leaves the clause unread (`Cfg[ Owner !exists Kind == %k ]` over a map that lacks `Kind` is not refused with `let k = Parameters.Kind` as it is not with `let k = 'k'`: `Kind == %k` is read and fails either way), and an unread clause never counts against the predicate, so the readable clauses decide and such a filter is refused where its absence clause holds on the map, the fail-closed side. The two spellings of that filter read differently, and the asymmetry is the shipped reading: the literal `spec[ ... ]` is refused where the key spelling passed a scalar over, while the bound spelling, `%s[ securityContext !exists ]` with `let s = spec`, announces the moved selection instead and is read by its notice: it selects nothing and writes the `DEPRECATION` notice below, `empty` passes and a `when ... !empty` gate is `SKIP` (KNOWN_ISSUES item 11 records the asymmetry).

Before 3.2 this spelling tested the bound map itself, so the predicate held and `%auth` selected the map, while the literal `Resources.WebServer[ ... ]` selected nothing. Since 3.2 the two agree, and a rule that relied on the old reading has its filter select among the map's entries instead: an entry the predicate holds on is selected in the map's place, an entry it rejects is not, and a scalar entry, such as the resource's `Type` string, is passed over, neither selected nor reported, as it is under the literal `Resources.WebServer[ ... ]`, `.*` and `[*]` (the alias and the literal part on a map that holds scalars beside sub-maps under an absence predicate: `let s = spec` with `%s[ securityContext !exists ] !empty` opens its gate on the sub-maps of a Deployment `spec` whose `replicas: 3` sits beside them and fails a `spec` with no `securityContext` in the body, while the literal `spec[ securityContext !exists ] !empty` is refused there, fail closed, since the predicate holds on the `spec` itself and the sub-maps it kept beside the scalar it passed over may be the fields of one object, which the refusal says and remedies: `spec[*][ securityContext !exists ]` to read the spec as one object, the one spelling it names there since no sub-map holds `securityContext` and `spec.*[ securityContext !exists ]` would keep the same sub-maps again (where a sub-map does hold the key it names `spec.*[ ... ]` for the members and `spec.securityContext !exists` for the map itself instead); `.*` reads the members under every map, and over a map with no member its empty answer is the members reading, not a verdict lost). A predicate about the value itself, `Labels[ k | this == 'prod' ]`, still tests a scalar entry and binds its key. A map whose entries are all scalars under a predicate that names a key the map itself holds is refused through the variable as it is after a key, naming the key (`%m[ Status == 'Enabled' ]` with `m` bound to `{ Status: Enabled }`). What the rule then reports depends on where the filter sits. A `when %auth !empty` gate over a selection of nothing no longer applies, so the rule it guards is `SKIP`, and so is an assertion over a selection of nothing: `%auth.Metadata."AWS::CloudFormation::Authentication".*.password !exists` is not applicable where it used to fail on the password, the fail-open direction and the one the notice below is for, and `%auth exists` is not applicable where it used to pass; over a selection of nothing `empty` passes where the selected map failed it, `!empty` fails where it passed, and `exists`, `!exists` and a comparison are not applicable where the selected map decided them (the old reading of `%auth` by a static read of the 3.2.1 sources, unmeasured against a built release; the three null-entry spellings below are the measured ones). An assertion over a selection compares the entries selected in the map's place: `%p[ Name exists ].Name == 'b'` over a map whose `Name` is `a` and whose `Inner` entry's `Name` is `b` used to compare `a` and now compares `b`. A null entry, a bare key such as `B:` beside a bucket, is handed to the predicate as the literal spelling hands it: an absence check holds on it, and an assertion over the selection then fails closed on the null member at exit 19 ("needed value at [null] was empty"), where in the released 3.1.12, 3.2.0 and 3.2.1 binaries the same absence check through the variable passed at exit 0 over that template, the bound map tested as one value and the null never reached, a PASS -> FAIL move the fixture rows `tags_absent_not_empty_through_a_variable.guard` and `tags_absent_not_empty_after_star.guard` over `bucket_beside_a_null_entry.yaml` record (the same check over two buckets with no null passes before and after); a value check fails on it and drops it, so the members beside it decide, and `%r[ Type == 'AWS::S3::Bucket' ].Properties.BucketName exists` with `let r = Resources`, `Resources[*][ Type == 'AWS::S3::Bucket' ].Properties.BucketName exists` and `Resources.*[ ... ]` pass at exit 0 over a `Resources` holding a bare key beside a named bucket. Of those three, the `.*` spelling failed in the released 3.1.12, 3.2.0 and 3.2.1 binaries (measured on binaries built from the release commits: the rule reads `FAIL`, and the released CloudFormation reporter then panics at exit 101, "internal error: entered unreachable code", in place of a failure text; the retrieval error "Filter on value type that was not a struct or array" the README's bullet names was read on 3.2.1's type-block line over the list document), so for it this is a change from a release; the `[*]` spelling was not applicable at exit 0 in those releases (observed: their `--verbose` trees evaluate the filter's predicate against the member produced by a `.*` before the wildcard that precedes the filter, or the document root when there is none (the document root here), where no null is reached and no `Type` is found), and the variable spelling was not applicable at exit 0 as well (observed: the trees test the bound `Resources` map as one value, its own change above), so for those two the move is from a selection of nothing to a selection among the members. The direction differs by spelling: for `.*` a failure is lifted (`FAIL` and the reporter panic, then `PASS`), the fail-open direction; for `[*]` and the variable spelling a rule that was not applicable now decides, `PASS` over a bucket that holds `BucketName` and `FAIL` at exit 19 over one that lacks it (the current verdict observed on `bucket_name_exists_after_star.guard` over `bucket_without_a_bucket_name.yaml`; that the releases were not applicable over that document too is inferred from the mechanism their trees show over the other documents, the predicate evaluated against the document, where no `Type` is found whatever the bucket holds), the fail-closed direction. All three move into agreement with the literal `Resources[ Type == 'AWS::S3::Bucket' ].Properties.BucketName exists`, which passed in every release (observed), and with a type block (`AWS::S3::Bucket { Properties.BucketName exists }`, inside a rule or at the top level), which passed over this template in 3.2.1 (observed; 3.1.12 and 3.2.0 refused a type block inside a rule outright, "Unable to resolve type block query: AWS::S3::Bucket", at exit 255). Over a `Resources` written as a list with a null element the variable and the literal spellings passed in those releases as they pass now, while `[*]` was not applicable at exit 0, `.*` failed with the same reporter panic, and in 3.2.1 the type block was not applicable at exit 0 (its reason line reading "no AWS::S3::Bucket could be selected from the input: Filter on value type that was not a struct or array null /Resources/1"); all five pass over the list now.

**Behavior change in 3.2: a filter after a key over a map with a scalar entry.** Earlier versions handed every entry of the map to the predicate, scalars included, so over an all-scalar `Properties` the clause `Resources.B.Properties[ Foo !exists ] !empty` selected every property by the absence of `Foo` and passed, and `when Resources.B.Properties[ Foo !exists ] !empty { ... }` opened its block.
Since 3.2 a predicate about keys passes a non-null scalar entry over, under the literal `Key[ ... ]` as under `.*`, `[*]` and a variable; over the all-scalar `Properties` the filter passes every property over, keeps nothing, and the predicate holds on `Properties` itself by the absence of `Foo`, so it is refused in both polarities, defining `X` and naming the `X[*][ ... ]` remedy (`X.*[ ... ]` for the members and `X.Key !exists` or `X.Key empty`, the predicate's own absence operator, for the map itself where a map-valued entry was rejected, or kept while some sub-map, the kept one included, holds a key the predicate names): `!empty` and `empty` fail, and the `when` gate fails rather than opening or skipping.
A predicate that compares the entry itself (a bare `this` under any operator: `this == 'prod'`, `this !empty`, `this exists`, alone or beside a clause that names a key; `this !empty` and `this exists` count only as the whole predicate or an `or` arm of it) still tests the scalar, so `labels[ this !empty or env exists ] empty` over `labels: { team: '', tier: web }` keeps `web` as `labels[ this !empty ] empty` does, and adding a disjunct never makes a filter select less (after a key or a `%name` only: under `.*` and `[*]`, a walk over members, a bare `this` that asks no more than `exists` or `empty` leaves a scalar entry passed over and an all-scalar map enumerated when the predicate names a key the map lacks, so `Resources.*.Properties.*[ "Fn::ImportValue" exists or this empty ] empty` reads as `Properties.*[ "Fn::ImportValue" exists ] empty` does over an SQS queue: passing a queue of scalar properties, passing one with a map-valued `RedrivePolicy` beside an int, failing one whose `QueueName` imports a value); a scalar so handed on and kept THROUGH a key absence it holds vacuously (`Properties[ Foo !exists or this !empty ] !empty` over an all-scalar `Properties`: `Foo !exists` holds on a string for want of any key, so every property was selected and `!empty` passed, the pre-3.2 reading back through the `this` hand-off) is refused in both polarities, WHATEVER the `this` clause beside the absence is and whatever it decided: an `or` arm (`Foo !exists or this == 'b'` selects exactly what `Properties[ Foo !exists ]` selects, since the absence arm keeps every scalar by itself), a comparing conjunct that rejects some scalars and keeps others (`Foo !exists  this == 'b'` over `{ BucketName: b, Region: us-east-1 }`, `this empty  env !exists`), one every scalar satisfies (`this != ''`, `this is_string`, `this != 'slow'  Owner !exists` over `{ Mode: fast }`; a `Tier: web` beside `Mode` changes nothing), a negated type test a map satisfies too (`this !is_list`, `this !is_int`, `this !is_string` over a mixed map: one reading passed these because it asked the map read as one object, whose answer to a bare `this` the predicate's shape fixes), an `or` of `this` comparisons or of a `this` clause with a key clause (`Foo !exists  this == 'b' or Bar exists`), and a `Properties` that holds the very `Foo` the absence clause names; the one sentence names the absence clause and the first property the filter kept, claims nothing about what the `this` clause decided, and its remedy asks the two questions apart: `X.Key !exists` for the map itself and `X[ ... ]` with the absence clause left out for the entries (`X.*[ ... ]` too where the map holds a member; beside a sub-map that holds a key the predicate names, `X.*[ ... ]` with the `this` clause left out reads the members), never `X[*][ ... ]`, which over a map of scalars reads one object and passes on every template; a `this !empty` or `this exists` conjunct beside other clauses (or the same by `not`: `not this empty`, `not this !exists`) hands no scalar over, since it decides nothing a non-empty scalar fails, while `this empty` and `this !exists` fail every non-empty scalar and are handed over as `this == 'x'` is, so `Properties[ this !empty  Foo !exists ] !empty` is refused as `Properties[ Foo !exists ] !empty` is, and `Properties[ Foo !exists  this != '' ] !empty` over the same all-string properties is refused with it; a predicate whose only absence-shaped clause is a bare `this empty` (`labels[ this empty ]`) tests each string's own value, keeps nothing vacuously and is decided for real; an all-scalar map under a predicate that names one of its own keys is refused, as before; and a null entry, a bare key, is handed to the predicate under every spelling.
A rule that asked the map about its own key through its entries, `Properties[ Foo !exists ]`, is written `Properties.Foo !exists`.

When the filter did not select the map it used to select -- the predicate holds on a map the variable holds, in a way the rule relied on (a key the predicate names was found on the map, even when a filter or wildcard after it selected nothing, as in `Properties.Tags[ Key == 'Owner' ] empty` on a bucket with no Owner tag, or a lookup got into the map before the key it names was missing, as in `Properties.BucketEncryption !exists` on a bucket whose `Properties` has no `BucketEncryption`; a pass that found nothing of the map is announced or not as "When the notice stays quiet" below says), and the map is not among what the filter selected -- Guard writes a `DEPRECATION` notice to stderr naming the `let` (or the parameter and its rule) and the filter as written, the map that lost its selection and how many of its entries were selected in its place, the filter's position and the two rewrites. The verdict does not move. A `let` bound to a function call (`let doc = json_parse(...)`), a `let` bound to a map written out in the rules file, and a parameter bound to either at its call site (`check(json_parse(...))`) lose a selection the same way and are announced the same way, with the differences their binding makes: the call is printed as written and the literal is elided to `let policy = { ... }`; a parsed map is named by the property it was parsed from and a literal map by no path, since the document holds neither; and the second rewrite is to filter a collection the map holds (`%doc.<key>[ ... ]`), since there is no parent path to bind. One line per filter, however many maps the variable holds and however many test cases evaluate the file, and one per filter site across the data files of one `validate` run, with the `NOTE:` trailer for a site later files also drew; how the line and the trailer are written is described once, under [How `validate` writes notices](#notices). A binding that projects, such as `Resources.*[ ... ]`, is announced when its filter walked the selected values' entries -- the author's own `[*]` before the filter, or a key after the projection as in `Wrapper.*[ Marker == 'x' ].Config` and `Resources.*[ Type exists ].Properties` -- because the old reading selected each map it held the same way; `%b[ ... ]` straight after a projection still tests each selected value as a whole and is not announced.

##### When the notice stays quiet

The notice is for a selection a rule relied on. It is not raised:

- when the predicate does not hold on the map and the map is a collection, or an object over whose fields the filter selects nothing: the previous reading selected nothing there either, as for `let r = Resources` filtered for a `Type` the template lacks (the resources share `Type`, a collection), or `let s = spec` with `%s[ replicas == 3 ]` over a Deployment `spec` whose fields have no `replicas`. The one shape that moved here is announced: an object (an entry that is not a map, or sub-maps that share no key name) on which the predicate does not hold because the object carries the checked key, while the walk selects the fields that lack it. `let s = spec` with `%s[ securityContext !exists ]` over a `spec` that carries a `securityContext` sub-map: the object has the key, so the previous reading selected nothing and `%s[ securityContext !exists ] empty` passed, while a `when %s[ securityContext !exists ] !empty` gate was `SKIP`; `selector`, `template` and the `securityContext` sub-map itself each lack a `securityContext` of their own, so the walk selects all three, `empty` fails and the gate opens. The notice names the selection gained, the map and the binding, with the same two rewrites. It goes out only for a selection held by absence, every selected field lacking the key; a positive predicate that selects the entry carrying what it asks for (`let m = Resources.Only` with `%m[ Metadata."AWS::CloudFormation::Authentication" exists ]` selecting the `Wrapper` entry that holds the path) is the reading described above and is not announced;
- when the predicate held on the map only because a key it names is missing from the map (`empty` or `not exists` over a key the map does not have) and the map is a collection of items the predicate is about, which Guard reads from the entries themselves: every entry is itself a map on which the predicate held, through a key the entry carries or for want of the key. `let r = Resources` with `%r[ Properties.Tags empty ]` over untagged buckets is this case. `Resources` has no `Properties`, every resource under it does and lacks `Tags` beneath it, the author meant the resources, and the earlier reading's selection of the whole `Resources` map failed compliant templates for nothing; a notice there would tell authors to rewrite a rule written the way this document recommends. Under the population alias -- `let r = Resources`, an alias of it (`let all = Resources` then `let r = %all`), or a parameter passed either -- an entry that carries the key and fails the check is still a member too: `%r[ DeletionPolicy !exists ]` over resources none of which carries the key (the check holds on each) and over resources one of which does (found there, holds elsewhere) is quiet either way, and so is the idiom over a compliant, tagged template; a populated template does not flip the notice. Under a variable the author named -- `let p = Resources.LT.Properties`, a nested collection such as `let r = Template.Resources`, a parameter bound to either -- an entry the predicate held on is a member, and a sub-map that carries the very key the author checked absent makes the map an object: the lost selection is announced. `let p = Resources.LT.Properties` with `%p[ TagSpecifications !exists ]` over a `Properties` holding only a `LaunchTemplateData` sub-map that carries the key, the notice's own example, used to open its `when ... !empty` gate and fail on a missing `LaunchTemplateName` and is now `SKIP`, announced; against the released 3.2.1 the move is the same for a `Properties` that also carries a scalar `LaunchTemplateName`: 3.2.1 tested the bound map itself, found no `TagSpecifications` on it, selected it, opened the gate and ran the guarded rule (inferred from the reading this section describes; the released `--verbose` trees observed on the fixtures under `guard/resources/validate/wildcard-filter-release-verdicts/` test a bound `Resources` map as one value the same way), where the gate is `SKIP` at exit 0 now (observed on `tag_specifications_absent_gate_through_a_variable.guard` over `launch_template_with_tag_specifications.yaml`), and the assertion form over all-scalar properties lacking the key, `%p[ Tags !exists ] !empty` over `{ BucketName: b }`, fails at exit 19 where 3.2.1 passed it (the same inference; the current verdict observed on `tags_absent_not_empty_through_a_variable_bound_to_properties.guard` over `scalar_properties_without_tags.yaml`). Two or more sub-maps are a collection only when they are the same kind of thing, which Guard reads as a key name every one of them carries (`Type` on the resources of a template, a `Config` on each of a map of configs); sub-maps that share no key name are the fields of an object, and an absence check that holds on each of them for want of the key is a check about the object: `let d = Resources.LT.Properties.LaunchTemplateData` with `%d[ MetadataOptions !exists ]` over `Monitoring` (`Enabled`) and `IamInstanceProfile` (`Name`) sub-maps is announced, as is `let s = spec` with `%s[ securityContext !exists ]` over a Kubernetes Deployment `spec` of `selector` and `template` (the same `spec` carrying a `securityContext` sub-map is the gained selection of the first bullet, announced from the other direction). A map of sub-maps that lack the checked key and share some other key still reads as a collection, and [KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 11 records that limit. The same rule reads a nested collection, and that is a listed limit of this notice ([KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 11): `let r = Template.Resources` with `%r[ Properties.Tags empty ]` over a nested template whose buckets carry `Tags`, or with `%r[ DeletionPolicy !exists ]` over one whose resource carries the key, draws the notice although the author meant the resources, while the same rules file over a nested template whose resources lack the key is quiet, so the template decides the notice there. Guard reads the entries and the binding's shape and cannot tell a nested collection from an object of sub-maps by them; the alternative, reading entries that all carry a scalar `Type` as a population whatever bound the map, which would quiet nested templates and still announce the launch-template example, is not built, because the notice is a deprecation line at exit 0 and the verdict does not move with it. (An earlier reading counted a sub-map the predicate reached into as a member whatever bound the map, which kept the launch-template example above quiet while its gate closed.) A null entry, such as a bare `Placeholder:` resource with no body, is a member with nothing to read and is passed over: it neither makes the collection an object nor keeps the notice quiet on its own; an empty-map entry, `Placeholder: {}`, is the same empty resource spelled the JSON way and is passed over the same way, by the shared-key test as by the entry reading, so the idiom is quiet over either spelling. An entry under an intrinsic directive key beside the resources, any key with the `Fn::` prefix (`'Fn::Transform': { Name: 'AWS::Include', Parameters: { ... } }`, the common one; under `AWS::LanguageExtensions` a list-valued `'Fn::ForEach::Buckets': [ ... ]`; a map-valued `Fn::ImportValue` written where a member would be), is an instruction to the service, not a member: every reading of the map's entries passes it over, the shared-key test, the object-of-fields test and the per-entry probe alike, so a template that includes a snippet or loops over a list this way keeps the idiom quiet, where the transform's `Name` and `Parameters` keys would otherwise have read as a field sharing nothing with the resources, and the ForEach list as a scalar field, and announced the notice over a compliant template. The rule is the prefix, not the one name; matching `Fn::Transform` alone would read a map with any other `Fn::` key beside its members as an object, and [KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 11 records that alternative. An empty map, or a map whose entries are all null or all empty maps (`Properties: {A: {}, B: {}}`, the JSON spelling of `A:` and `B:`), has no entry to read, and there the binding decides: `Resources: {}` is quiet, with nothing to lose, through any variable that names a top-level key (directly, through an alias chain or a parameter), while an empty map the author named is announced, as `let p = Resources.Q.Properties` with `%p[ KmsMasterKeyId !exists ]` over `Properties: {}` is, because the earlier reading selected the map and a `when` over the selection ran, where the selection is now empty and the rule is `SKIP`. An empty map, or one whose entries are all null or all empty maps, carries nothing Guard could read a population from, so that rule has two shapes it cannot tell apart, both listed in [KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 11: an empty top-level object such as a Kubernetes `metadata: {}` under `let md = metadata` names a top-level key and stays quiet although a `when` gate over `%md[ labels !exists ]` closed where it used to open (a populated `metadata` is announced, from its scalar entries), and an empty nested collection, `let r = Template.Resources` over `Template.Resources: {}`, is announced although the same rule over a nested collection whose entries hold the check through a key they carry is quiet. The same pass on a map that is not such a collection -- an entry that is a scalar, or an entry the predicate never reached into -- is a check the author wrote about the map itself under any binding, the earlier reading's selection of it was one the rule relied on, and it is announced: `let md = metadata` with `%md[ labels !exists ]` on a Kubernetes `metadata` map of scalars; `let p = Resources.Bucket.Properties` with `%p[ Tags !exists ]` on a properties map of scalars; `let p = Resources.LT.Properties` with `%p[ TagSpecifications !exists ]` where a scalar `LaunchTemplateName` sits beside the `LaunchTemplateData` sub-map. In a disjunction the question is asked of the clause that passed: in `%r[ Bucket.Type == 'X' or Properties.Tags empty ]` the failing `Bucket.Type` clause does not count, although it found a key of `Resources`;
- when the predicate, or a `when` block or nested block inside it, names another rule or a variable, declares a `let` of its own, or compares against a function call: such a predicate cannot be re-run quietly, so it is not probed and a lost selection there goes unannounced. A `when` block or nested block whose clauses do none of these is probed like a bare clause, and a `when` block whose condition does not hold on the map neither holds nor fails the predicate, as it neither holds nor fails the filter;
- when the filter is on a literal path, or when the variable holds a list: neither lost a selection.

**Behavior change in 3.2: a variable bound to another variable that names a top-level key.** `let all = Resources` then `let r = %all` is read as `Resources` wherever `%r` is used, as a parameter passed `%all` already was. A filter or `.*` over `%r` on a template with no `Resources` key, or an empty one, is an empty selection and the clause is not applicable, as it is for `let r = Resources` and for `Resources` written out; earlier versions failed such a clause through the alias (`%r.*[ Type == 'AWS::S3::Bucket' ].Properties.BucketName == 'b'` exited 19 over `{}` and over `Resources: {}`) and passed a `!exists` or `empty` assertion over the same selection, where both are now not applicable. The direct spelling did not move. No notice marks this move: a document with no resources holds no map a filter could lose.

To test the map, move the predicate into the `when` condition:

```
let m = Resources.WebServer
rule authentication_has_no_password when %m.Metadata."AWS::CloudFormation::Authentication" exists {
    %m.Metadata."AWS::CloudFormation::Authentication".*.password !exists
}
```

To select from a collection, bind one and filter that:

```
let auth = Resources.*[ Metadata."AWS::CloudFormation::Authentication" exists ]
rule authentication_has_no_password when %auth !empty {
    %auth.Metadata."AWS::CloudFormation::Authentication".*.password !exists
}
```

Both fail on an instance whose authentication block holds a `password`, and neither raises the notice. They are not interchangeable: the first checks only the instance it names, passing while a launch configuration beside it holds a password, and is `SKIP` on a template that has no `WebServer`; the second checks every resource that carries the block, whatever its type or logical id, failing on that launch configuration and passing on a template whose blocks hold no password.

#### Comparing against a query that resolves to no values

When the RHS of a binary operator is a query, it can resolve to no values at all. This usually happens because the query selects a resource type that the input does not contain:

```
# %denied is empty for any template that defines no KMS keys
let denied = Resources.*[ Type == 'AWS::KMS::Key' ].Properties.KeyId

rule bucket_name_is_not_denied {
    Resources.*[ Type == 'AWS::S3::Bucket' ].Properties.BucketName != %denied
}
```

There is nothing to compare the LHS against, so the clause cannot be decided and it `FAIL`s. This applies to both polarities: `IN %denied` and `!= %denied` both fail when `%denied` resolves to no values. The failure message says that the reference resolved to no values, so the fault is not mistaken for one in the input.

Failing here is deliberate, and it is a change from earlier versions, which reported `SKIP`. A `SKIP` exits `0` and is indistinguishable from a `PASS` at a CI gate, so the rule above reported success for every template while comparing nothing, including a template whose bucket name was on the denylist that the query failed to populate.

If a query is expected to resolve to no values, state that with a `when` guard. The condition fails, so the rule does not apply and is reported as `SKIP`:

```
rule bucket_name_is_not_denied when %denied !empty {
    Resources.*[ Type == 'AWS::S3::Bucket' ].Properties.BucketName != %denied
}
```

This is the same `when %query !empty` idiom used to scope a rule to templates that contain the resources it checks. A comparison written directly as a `when` condition is also reported as `SKIP` rather than `FAIL` when its reference is empty, because a failing condition would drop the block it guards.

A right-hand query that stops at a key the document lacks (`Parameters.Missing.Default` over a template with no `Parameters`) is a value the document lacks rather than a query with no values, and a comparison against it is a decided failure for each left-hand value, under every comparator and in both polarities, with the path the retrieval stopped at as the reason. `some` changes nothing here: with no left-hand value that passed, `some Resources.*.Properties.Name != Parameters.Missing.Default` fails as an assertion, reports its rule not applicable as a `when` condition, and deselects every entry as a filter predicate. The escape hatch is the one above, spelled for the reference: `when Parameters.Missing.Default exists { ... }`. With a left-hand value that passed against a resolved right-hand value beside the absence, `some` passes on that pair while the `match_all` spelling is not applicable (`some Port != <selection>` over `Port: 22`, one resource whose selection is absent and one whose selection holds `80`): one left-hand value, two statuses, and the quantifiers read them differently. So a reference the document lacks beside a MARKER (a map a key filter's regex could not decide, or a refused read) among the right-hand values, with no resolved value beside them, decides `match_all` (the absence's failure stands whatever the marker hides) and is raised under `some`, in both polarities, since the marker's pair may be the one the value passes against (pinned by `an_absent_right_hand_reference_beside_a_marker_is_raised_under_some_and_decided_under_match_all`).

**Behavior change in 3.2: `some` against a right-hand query the document lacks.** Earlier versions filed, beside each left-hand value's failure against the absent right-hand value, a second verdict for the comparison that never ran, which the negated comparators turned into a pass, so `some ... != <absent query>` and `some ... NOT IN <absent query>` passed on the strength of it: the assertion reported PASS at exit 0, the `when` condition held and ran its body, and the filter predicate selected every entry. 3.2 files the failure alone, with no hold and no notice, because a pass about a comparison nobody made was not an answer to the question the clause asked; the `match_all` spellings never moved. The moves, by fixture rule under `guard/resources/validate/in-over-enumerating-query/` with `names_without_parameters.yaml`:

- `some_name_ne_absent_param.guard` (`some Resources.*.Properties.Name != Parameters.Missing.Default` asserted): PASS at exit 0 to FAIL at the validation failure code.
- `some_name_not_in_absent_param_gate.guard` (the `NOT IN` spelling as a `when` condition): the body ran and the rule reported PASS; the rule is now reported not applicable, SKIP at exit 0.

**Behavior change in 3.2: a comparison whose right-hand side holds an undecidable marker beside resolved values or absent operands.** The marker is a refused `%name`'s, or the one a key filter leaves for a map whose keys it could not read (a regex out of budget), standing among the right-hand values of `==`, `!=`, an ordering, `IN` or `NOT IN`. The baseline of every move below is the RELEASED version, named once here: each bullet states what the release answered for the shape and what 3.2 answers. 3.2 reads the marker pair by pair beside what the resolved pairs and the absent operands decide, and only a clause nothing else decides fails closed on it. The moves, each with the test in `guard/src/rules/eval_tests.rs` that pins it (named as "pinned by" after the move):

- `when Y IN <selection with a marker>` with `Y` equal to a resolved value: the rule failed at the validation failure code; it now runs its body (PASS when the body holds), because a listed value decides membership whatever the unread map holds (pinned by `a_key_filter_marker_on_the_right_decides_membership_and_set_equality_as_a_refusals_does`; the passing clause carries no failing child record, pinned by `a_passing_membership_beside_a_marker_carries_no_failing_child_record`). The assertion `Y IN <selection with a marker>` passes the same way, and when the marker is a refused read's the refusal is registered and reported on stderr beside the pass rather than raised (pinned by `a_membership_a_listed_value_settles_reports_the_refused_read_beside_it`); a reference the document lacks beside the same listed value still fails the membership, so a refused read is reported where an absence fails (the same test's control case; the two readings stand as released, their parity a question for a later release). With `Y` equal to no resolved value the rule still fails closed, since the unread map may hold `Y`.
- a refused read beside a value that does NOT match: `[ Properties.Owner == %names ]` over an `Owner` no listed pair equals, `when Cfg.Mode == %x` with a resolved mismatch, `when some Names[*] NOT IN %x` with every name colliding. The released 3.1.12, 3.2.0 and 3.2.1 binaries, built from the release commits and measured, read the two `when` conditions not applicable at exit 0 and reported the refused read nowhere, and stopped on the filter predicate with an internal error (`entered unreachable code`, a panic at an arm of the evaluator) before any verdict. 3.2 lets the resolved no decide (a decided no beside an undecided pair is no), so the predicate deselects the entry and the condition is not applicable, at exit 0, and the refused read in `%names` or `%x`, which that verdict never raised, is registered and reported on stderr in the line's mismatch wording, "was decided by a value that does not match" under `==`, an ordering or `IN`, and "was decided by a value that matches a denied value" under `!=` and `NOT IN`, where the deciding value equals a listed entry (pinned by `a_refused_read_beside_a_decided_mismatch_is_reported`). Whether a value that does not match decides the clause is the comparator's question, answered once for the verdict and for the line: under a positive `IN` a no decides nothing beside the marker (the entry it hides may be the one the value is among), so `Owner IN %names` with `Owner` equal to no listed value fails on the marker's own pair, whose record names the refusal, and writes no line, as `Owner NOT IN %names` does with a value no listed entry matches; a reference the document lacks among the values is the pair's own decided failure, never "a value that does not match", and a marker beside it keeps its record (pinned by `a_membership_that_fails_beside_the_marker_writes_no_line_and_keeps_the_markers_record`).
- `some X NOT IN %x` and `some X != %x` beside a marker of either kind (a refused read's, or a key filter's), `X` equal to no resolved value: PASS at exit 0 to FAIL at the validation failure code, because the pass a value reads beside the marker may be against the very value the marker hides (pinned by `a_markers_pair_keeps_its_failing_status_under_a_negated_membership_in_every_role`, `a_some_clause_beside_a_refused_value_is_never_eligible_for_the_notice` and `a_refused_right_operand_decides_by_the_comparator_and_the_quantifier`); `!=` reads the key filter's marker as `NOT IN` does, so the two spellings agree (pinned by `a_key_filter_marker_reads_alike_under_not_equal_and_not_in` and `a_key_filter_marker_on_the_right_is_read_pair_by_pair`); a resolved match under the negated comparator stays a decided no.

## <a name="notices"></a> How `validate` writes notices

A `DEPRECATION:` notice on stderr, about a reading that changes in a later release or that this release has replaced for a shape the notice names (the list-twin notice: the one-object reading of a pair-shaped filter over a map of scalars is retired, and the twin's verdict stands), describes the rule, not one evaluation of it, so `validate` writes each once per run. The line about a `let` read behind a chain of more than 16 `let`s (KNOWN_ISSUES.md, "Runtime notices carry no provenance") is written on this channel too though nothing is deprecated, because the once-per-run channel is the one the engine has for a notice about the rules file as written; a channel of its own would be a new line shape on stderr, a contract change left for a later release. The one exception is the moved-reading `Warning:` line about a key filter's function argument (see FUNCTIONS.md), which is kept per data file: each data file whose reading moved gets its own line beside its own report, naming that file, and the trailer described below never names a file for it. The other `Warning:` lines, about a condition the run went on from, are written where the condition is met. The refused-read line is one of them, written once per clause site and never a deprecation: when a comparison is decided without raising a REFUSED read (a `%name` whose selection was refused) that stands among its values, on either side, because a value the document lacks (a left-hand value the document does not hold, an empty collection, a right-hand reference that resolved to nothing) decided it, because a listed value settled a membership, because `some` passed on another of its values, or because a value that does not match (a resolved mismatch under `==`, an ordering or `IN`), a value that matches a denied value (a collision under `!=` or `NOT IN`) or a value of another kind (a pair the comparator refused on kinds under `!=` or `NOT IN`) decided it, and no pair is left undecided, `validate` writes one `Warning:` line naming the clause as written, how it was decided (by a value the document lacks, by a value that holds, by a value that does not match, by a value that matches a denied value, by a value of another kind, or several of these with the count of evaluations each way), every distinct refusal's own sentence (one named as it is; several numbered, `(1) ... (2) ...`, in the order the site met them), and the clause's position with the data file it was found in, beside the file's report; and a refusal beside an absence is also written into the record of the value that decided the comparison, after the retrieval's own reason, and printed whole by the console; the line names the distinct refused reads the site met, so one refusal met beside a pass and beside an absence is one refusal whatever the order of the resources; a clause that is raised on a pair nobody could decide carries every refused read that stood among its comparison's values in its failure (a `let`-bound selection holding a key filter's refusal is read as its values inside a filter predicate, and refused on that one sentence at its bare read outside one, before any pair is compared; one named as it is; several numbered, `(1) ... (2) ...`, in the order the site met them, the right-hand refusals before a left-hand marker's; a reason that is no refusal and leads the raise, a key filter's marker or a spent regex budget beside one refusal, is numbered with it, `(1) <reason> (2) <refusal>`) and writes no line, though each is registered for the error that carries them, and the numbered text is accepted by the refusal test as a whole, part by part, without being registered itself (so the refused reads the run counts stay the refusals met, never the text that joined them), for the asserted raise and for a `when` condition's or a filter predicate's raise alike; and the marker a key filter leaves for a map it could not decide is not a refusal, so beside such a decision its reason goes into the record alone and no line is written. A notice recorded for a site in the rules file (a filter through a variable, a `when` over a function's result in each direction it moved, a function call over a list argument) is written once per site across every data file of the run, and a notice with no site once per distinct text, however many data files draw it. Both outputs keep that set: the structured reports (`-o json`, `yaml`, `sarif` or `junit`, and `--structured`) write the set once on stderr, before the document, with nothing for the later files; the single-line output writes each notice beside the first data file that drew it and, after its last file, one `NOTE:` trailer per distinct list of later files that drew a notice the run announced once (`NOTE: also drawn by <files>: <notice>; <notice>`). The trailer names at most three of those files and counts the rest; when two trailers' shortened lists would read the same, each adds the first file its list lacks that the other's holds (`and 195 more, not t60.yaml`), so a line never grows with the directory. It names each notice so a reader can match it to the line above: a filter notice or a list-argument notice by its kind and site, a gate notice by its kind, its direction and its site, a notice with no site by its opening words and the position it ends with. A notice one file drew gets no trailer, and the trailers are written before an error in a later data file is reported. The trailer is a notice too, so a library caller never sees it in a failure text, and it is not a deprecation: a count of `DEPRECATION:` lines is the notices alone.

## Custom Message

You can add a custom message to a clause. A custom message is added at the end of a clause as follows:

```
  <query> <operator> [query|value literal] [custom message]
```

`custom message` is expressed as `<<message>>` where message is any string which ideally provides information regarding the clause preceding it. This message is displayed in the verbose outputs of the validate (provide links) and test (provide links) commands and can be used to supply information helpful for understanding/debugging rules file evaluation on hierarchical data. The Template-2 example template clauses with custom message will look as follows:

```
Resources.NewVolume.Properties.Size IN r[50,200]
<<
    EC2Volume size must be between 50 and 200,
    not including 50 and 200
>>
Resources.NewVolume.Properties.VolumeType IN [ 'io1','io2','gp3' ] <<Allowed Volume Types are io1, io2, and gp3>>
```

A message written across several lines ends at the first later line that starts with `>>` (leading whitespace aside); whatever follows that `>>` on the same line is read as rule text, so a message body line may not itself start with `>>`. A message body may not contain `<<`; see [Known Issues](KNOWN_ISSUES.md) for what that excludes.

### Combining Clauses

Now that we have a complete picture of what constitutes a clause, let us learn to combine clauses. In Guard, each clause written on a new line is combined implicitly with the next clause using conjunction (boolean `and` logic):

```
# clause_A ^ clause_B ^ clause_C
clause_A
clause_B
clause_C
```

You can also combine a clause with the next clause using disjunction by specifying `or|OR` at the end of the first clause.

```
  <query> <operator> [query|value literal] [custom message] [or|OR]
```

Disjunctions are evaluated first followed by conjunctions, and hence Guard rules can be defined as a conjunction of disjunction of clauses that evaluate to a `true` (`PASS`) / `false` (`FAIL`). This can be best explained with a few examples:

```
# (clause_E v clause_F) ^ clause_G
clause_E OR clause_F
clause_G

# (clause_H v clause_I) ^ (clause_J v clause_K)
clause_H OR
clause_I
clause_J OR
clause_K

# (clause_L v clause_M v clause_N) ^ clause_O
clause_L OR
clause_M OR
clause_N
clause_O
```

This is similar to the [Conjunctive Normal Form (CNF)](https://en.wikipedia.org/wiki/Conjunctive_normal_form).

All clauses written based on the Template-1 example template can be combined as follows:

```
Resources.S3Bucket.Properties.BucketName is_string
Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
Resources.S3Bucket.Properties.BucketEncryption exists
Resources.S3Bucket.Properties.BucketEncryption is_struct
Resources.S3Bucket.Properties.Tags is_list
Resources.S3Bucket.Properties.Tags !empty
```

All clauses above are combined using conjunction. As you can see, there is repetition of part of the query expression in every clause. You can improve composability and remove verbosity and repetition from a set of related clauses with the same initial query path using a query block.

## Blocks

### Query blocks

The above set of clauses can be written in block format as follows:

```
Resources.S3Bucket.Properties {
    BucketName is_string
    BucketName != /(?i)encrypt/
    BucketEncryption exists
    BucketEncryption is_struct
    Tags is_list
    Tags !empty
}
```

The above composition is referred to as query blocks as the query preceding the block sets the context for clauses inside the block. This improves composability and removes verbosity and repetition while writing multiple related clauses with the same initial query path.

### When blocks - When condition for conditional evaluation

Blocks can be evaluated conditionally using `when` blocks; `when` blocks take the following form:

```
  when <condition> {
      Guard_rule_1
      Guard_rule_2
      ...
  }
```

- The `when` keyword designates the start of the when block.

- `condition` can be any Guard rule. The block is evaluated only if the evaluation of the condition results in `true` (`PASS`).

Below is an example using the Template-1 example template:

```
when Resources.S3Bucket.Properties.BucketName is_string {
    Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
}
```

The clause within the when block will only execute if `BucketName` is a string. If the value for `BucketName` was being referenced from a Parameter as shown below, the clause within the when block will not be executed.

```
Parameters:
  S3BucketName:
    Type: String

Resources:
  S3Bucket:
    Type: "AWS::S3::Bucket"
    Properties:
      BucketName:
        Ref: S3BucketName
    ...
```

### Named rule blocks

Named rule blocks allow for re-usability, improved composition and remove verbosity and repetition. They take the following form:

```
  rule <rule name> [when <condition>] {
      Guard_rule_1
      Guard_rule_2
      ...
  }
```

- The `rule` keyword designates the start of a named rule block.

- `rule name` can be any string that is human-readable and ideally should uniquely identify a named rule block. It can be thought of as a label to the set of Guard rules it encapsulates where Guard rules is an umbrella term for clauses, query blocks, when blocks and named rule blocks. The `rule name` can be used to refer to the evaluation result of the set of Guard rules it encapsulates, this is what makes named rule blocks re-usable. It also helps provide context in the validate (provide links) and test (provide links) command output as to what exactly failed. The `rule name` is displayed along with it block’s evaluation status - `PASS`, `FAIL`, or `SKIP`, in the evaluation output of the rules file:

```
# Sample output of an evaluation where check1, check2, and check3 are rule names.
_Summary__ __Report_ Overall File Status = **FAIL**
**PASS/****SKIP** **rules**
check1 **SKIP**
check2 **PASS**
**FAILED rules**
check3 **FAIL**
```

- Named rule blocks can also be evaluated conditionally by specifying the `when` keyword followed with a `condition` after the `rule name`.

Reiterating the `when` block example below:

```
rule checkBucketNameStringValue when Resources.S3Bucket.Properties.BucketName is_string {
    Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
}

# The above can also be written as follows
rule checkBucketNameIsString {
    Resources.S3Bucket.Properties.BucketName is_string
}
rule checkBucketNameStringValue when checkBucketNameIsString {
    Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
}
```

Named rule blocks can be re-used and grouped together with other Guard rules. Below are a few examples:

```
rule rule_name_A {
    Guard_rule_1 OR
    Guard_rule_2
    ...
}

rule rule_name_B {
    Guard_rule_3
    Guard_rule_4
    ...
}

rule rule_name_C {
    rule_name_A OR rule_name_B
}

rule rule_name_D {
    rule_name_A
    rule_name_B
}

rule rule_name_E when rule_name_D {
    Guard_rule_5
    Guard_rule_6
    ...
}
```

The above styles of compositions will be discussed in-depth in the [Guard: Complex Composition](COMPLEX_COMPOSITION.md) document.
