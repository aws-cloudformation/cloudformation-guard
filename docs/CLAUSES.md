# Guard: Clauses

Clauses are the foundational underpinning of Guard rules. Clauses are boolean statements which evaluate to a `true` (`PASS`)/ `false` (`FAIL`) and take the following format:

```
  <query> <operator> [query|value literal]
```

You must specify a `query` and an `operator` in the clause section:

- `query` in its most simple form is a decimal dot (`.`) formatted expressions written to traverse hierarchical data. More information on this section of the clause can be found in the [Guard: Query and Filtering](QUERY_AND_FILTERING.md) document.

- `operator` can use _unary_ or _binary_ operators. Both of these operators will be discussed in-depth later in this document:

  - _Unary Operators:_ `exists`, `empty`, `is_string`, `is_list`, `is_struct`, `is_bool`, `is_int`, `is_float`, `not(!)`
  - _Binary Operators:_ `==`, `!=`, `>`, `>=`, `<`, `<=`, `IN`

The `query|value literal` section of the clause is optional:

- `query|value literal` the third section of a clause is needed when a binary operator is used. It can be a `query` as defined above or it can be any supported value literal like `string`, `integer(64)`, etc.

Below are some examples for clauses:

- Clauses using unary operator:

```
# The collection TcpBlockedPorts cannot be empty
InputParameters.TcpBlockedPorts not empty
```

```
# ExecutionRoleArn must be a string
Properties.ExecutionRoleArn is_string
```

- Clauses using binary operator:

```
# BucketName must not contain the string "encrypt" irrespective of casing
Properties.BucketName != /(?i)encrypted/
```

```
# ReadCapacityUnits must be less than or equal to 5000
Properties.ProvisionedThroughput.ReadCapacityUnits <= 5000
```

## Operators

Let us look at Guard supported `operators` in-depth. Information on each operator will be accompanied by examples based on the following example CloudFormation template to help you understand the various operators. All examples in this section will be based on the following template:

```yaml
# Template-1
Resources:
  S3Bucket:
    Type: "AWS::S3::Bucket"
    Properties:
      BucketName: "MyServiceS3Bucket"
      BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault:
              SSEAlgorithm: "aws:kms"
              KMSMasterKeyID: "arn:aws:kms:us-east-1:123456789:key/056ea50b-1013-3907-8617-c93e474e400"
      Tags:
        - Key: "stage"
          Value: "prod"
        - Key: "service"
          Value: "myService"
```

### Unary Operators

#### `empty` and `exists` operators

Guard introduces `empty` and `exists` operators to assist authors verify states of the `query` in a clause. You can use the `not(!)` operator with both these operators to check the inverse state.

`empty`- Checks if a collection is empty. It can also be used to check if a query has values in a hierarchical data as all queries result in a collection, more about queries is mentioned in the [Guard: Query and Filtering](QUERY_AND_FILTERING.md) document.

```
# Checks if the template has resources defined
Resources !empty
```

```
# Checks if one or more tags defined
Resources.S3Bucket.Properties.Tags !empty
```

The above two clauses will `PASS` for the example template.

- The first clause checks to see if the template has resources defined under `Resources` , and the template has one resource with `S3Bucket` as the logical resource ID.
- The second clause checks to see if one or more tags are defined in `S3Bucket`. It has two tags defined under `Tags`.

`empty` can be used to check if string value queries have an empty string (`""`) defined.

On a value that cannot be empty — a number or a boolean — `empty` has no answer, so the clause fails and the report names the path and the operator. `not empty` fails as well: an integer is not empty, but reporting it as non-empty would accept a clause that never checked anything. Only the clause fails; the rest of the rules in the file are still evaluated and reported.

A `null` value is empty. `Properties.Encryption empty` passes when the template sets `Encryption: null`, and `not empty` fails on it, the same answers a key that is absent gets below. The key is still present, so `exists` passes on the same value. As a condition, `when Properties.Tags !empty` over a bare `Tags:` (which YAML reads as null) means the rule does not apply, exactly as it does when `Tags` is missing; it no longer fails the rule because the condition could not be answered.

`exists` - Checks if each occurrence of the query exists.

```
# Checks if BucketEncryption is defined
Resources.S3Bucket.Properties.BucketEncryption exists
```

The above clause will `PASS` for the example template as `BucketEncryption` is defined for `S3Bucket`.

> **IMPORTANT**: `empty` and `not exists` checks evaluate to true for missing property keys when traversing the input data. E.g. if we check `Resources.S3Bucket.Properties.Tags empty` if `Properties` was not present in the template for S3Bucket, then `empty` evaluates to true.

#### Array indexes

An index selects one element: `Items[0]` is the first and `Items[-1]` is the last, with `Items[-2]` the one before it. An index that names no element — past the end in either direction, or too large to be an offset at all — does not resolve, and the clause reports that rather than selecting a different element.

```
# the last tag, whatever the length of the list
Resources.MyBucket.Properties.Tags[-1].Key == "Owner"
```

#### `is_string`, `is_list`, `is_bool`, `is_int`, `is_float` and `is_struct` operators

`is_string` - Checks if each occurrence of the query is of `string` type.

```
# Checks if BucketName is defined as a string
Resources.S3Bucket.Properties.BucketName is_string
```

`is_bool` - Checks if each occurrence of the query is of `bool` type.

```
# Checks if ObjectLockEnabled is defined as a bool
Resources.S3Bucket.Properties.ObjectLockEnabled is_bool
```

`is_int` - Checks if each occurrence of the query is of `int` type.

```
# Checks if Port is defined as an int
Resources.ELBListener.Properties.Port is_int
```

`is_float` - Checks if each occurrence of the query is of `float` type.

```
# Checks if CompletionWindowMinutes is defined as a float
Resources.BackupPlan.Properties.BackupPlan.BackupPlanRule { CompletionWindowMinutes is_float  }
```

`is_list` - Checks if each occurrence of the query is of `list` type.

```
# Checks if Tags is defined as a list
Resources.S3Bucket.Properties.Tags is_list
```

`is_struct` - Checks if each occurrence of the query is a structured data.

```
# Checks if BucketEncryption is defined as a structured data
Resources.S3Bucket.Properties.BucketEncryption is_struct
```

`is_null` - Checks if each occurrence of the query is of `null` type.

```
# Checks if Resources.S3Bucket.Properties is null
Resources.S3Bucket is_null
```

All the above example clauses will `PASS` for the example template. You can use the `not(!)` operator with the above operators to check the inverse state.

### Binary Operators

Below are binary operators supported in Guard. The left-hand side (LHS) to the operator as mentioned above must always be a query and the right-hand side (RHS) can be a query or a value literal:

```
  ==    Equal
  !=    Not Equal
  >     Greater Than
  >=    Greater Than Or Equal To
  <     Less Than
  <=    Less Than Or Equal To
  IN    In a list of form [x, y, z]
```

A value literal can be from any of the following supported categories,

- all primitives `string`, `integer(64)`, `float(64)`, `bool`, `char`, `regex`
- a specialized range type for expressing `integer`, `float`, `char` ranges, expressed as,
  - `r[<lower_limit>, <upper_limit>]`, which translates to any value `k` that satisfies the following expression: `lower_limit` <= k <= `upper_limit`
  - `r[<lower_limit>, <upper_limit>)`, which translates to any value `k` that satisfies the following expression: `lower_limit` <= k < `upper_limit`
  - `r(<lower_limit>, <upper_limit>]`, which translates to any value `k` that satisfies the following expression: `lower_limit` < k <= `upper_limit`
  - `r(<lower_limit>, <upper_limit>)`, which translates to any value `k` that satisfies the following expression: `lower_limit` < k < `upper_limit`
- associative arrays (a.k.a map) for nested key value structured data like:

```
{ "my-map": { "nested-maps": [ { "key": 10, "value": 20 } ] } }
```

- arrays of primitive/associative array types

Comparisons are between values of the same kind, with one exception: `integer` and `float` compare against each other as numbers. That includes range membership, so `Size IN r[5.0, 100.0]` holds for a `Size` of `50` and `Size IN r[5, 100]` holds for a `Size` of `50.5`. `Size > 10` holds for a `Size` of `50.5`, and `Size == 50` holds for a `Size` of `50.0`. Earlier versions treated the two as different types and reported that they could not be compared, which failed the clause. Comparing across kinds that are not both numeric, a `string` against an `integer`, say, still cannot be decided, and the clause fails rather than guessing.

`null` is the other exception, for equality only. A `null` is equal to `null` and to no string, number, boolean, map or list, so `KmsKeyId != null` holds when `KmsKeyId` is set to anything else and `KmsKeyId == null` holds only when it is `null`. The same applies with the `null` in the template: a property written as `KmsKeyId: null` fails `KmsKeyId == "arn:..."` and passes `KmsKeyId != "arn:..."`, and it is in no list, so `KmsKeyId IN [...]` fails and `KmsKeyId NOT IN [...]` passes. A denylist is therefore satisfied by a property that is present and `null`; a rule that also needs the property set says so with `exists` or `!= null`. In short: a property that is present and `null` compared with `!=` to a non-null literal passes, and compared with `==` fails; a property that is absent still fails both, because a missing key is a retrieval failure rather than a `null`; and no notice is printed for either, since this is a change in what the comparison means rather than a deprecation. Earlier versions reported a `null` against any other kind as not comparable, which failed the clause in both polarities, so `!= null` could never hold. Ordering against `null` (`>`, `>=`, `<`, `<=`) and a `null` against a range or a regular expression still cannot be decided, and those clauses fail.

The distinction matters most inside a `when` condition. A condition that cannot be decided does not pass, and a rule whose condition does not pass is reported as not applicable, so the block it guards is never checked. A rule written as

```
rule large_volumes_are_encrypted when Resources.*[ Type == 'AWS::EC2::Volume' ].Properties.Size > 10 {
    Resources.*[ Type == 'AWS::EC2::Volume' ].Properties.Encrypted == true
}
```

now applies to a template whose `Size` is `50.5` as it always did to one whose `Size` is `50`.

A comparison across kinds that are not both numeric is a sharper problem in the same place, and one to be aware of when writing conditions. CloudFormation templates frequently carry numbers as strings, `Size: "50"` rather than `Size: 50`, and a string cannot be compared against `10`. The condition cannot be decided, so it does not pass, so the rule is reported as not applicable and the block it guards is never checked. The run exits `0`, exactly as it would for a rule that genuinely did not apply.

Guard reports which of the two happened. A rule skipped because a condition could not be decided says so, naming the operand kinds:

```
SKIP rules
large_volumes_encrypted_gate.guard/large_volumes_are_encrypted    SKIP
  large_volumes_are_encrypted: the rule did not apply because one of its conditions could not be decided: PathAwareValues are not comparable String, int
```

The same explanation appears under `not_applicable_reasons` in `--output-format json` and `yaml`.

A collection that is present and empty on the LEFT-hand side is a retrieval error, like a missing key, and a comparison over it fails on every binary operator in both polarities, `==`, `!=`, `<`, `<=`, `>`, `>=`, `IN` and `NOT IN`, with one exception: `==` and `!=` against a right-hand LIST compare the two lists as lists, so `[] == []` holds and `[] != [1]` passes, whether the list is written in the rule or resolved from the document; two document collections both empty are two lists too, so `Ports == SecurityGroupIds` over `Ports: []` and `SecurityGroupIds: []` holds and `!=` fails as a plain mismatch, neither naming an empty collection, where the orderings over the same pair flatten both lists to nothing and fail at the block level. `Ports IN [80, 443]` over a `Ports` of `[]` fails naming the empty collection; an empty list is not read as a subset of the set. Between two queries `==` and `!=` compare the empty list whole with each right-hand value: against a scalar right-hand value the failure names the kinds (`not comparable array, int`) rather than the empty collection, and against a right-hand list the exception above applies (`[] == []` holds, `[] == [1]` is unequal). Against a value written in the rule, `==` and `!=` name the empty collection for a scalar (`Ports == 80` over `Ports: []`) as the other comparators do, and compare two lists as lists for a list literal (`Ports == []` holds, `Ports == [1]` fails as a mismatch, `Ports != [1]` passes). A document `[]` on the RIGHT-hand side is a present value the left-hand values are compared against (`NOT IN []` passes each one), so it is an absence only for a left-hand value no comparison accepted; the behavior-change entry on a marker among a comparison's right-hand values, below, states that side. This is about collections the document resolved to: a `[]` written in the rule, inline or bound through `let`, is a value the author wrote and compares as one: a scalar compared with `==` or `!=` to a list literal is incomparable, in both polarities, so `Mode == []` and `Mode != []` over a string both fail on the kinds as `Mode == [1]` and `Mode != [1]` do; `[] == []` holds; and under `IN` a list literal reads element-wise whatever the right side's kind, so `[] IN [80, 443]` and `[] IN 80` are both false and `[] NOT IN [80, 443]` and `[] NOT IN 80` both true. In a `when` condition the same comparison is not satisfied, as it is not by a missing key, so the rule is reported not applicable and the reason names the empty collection (the kinds, where two-query `==` or `!=` compared it with a scalar), except that under the two-list exception above (a list literal or a list resolved from the document) the condition is decided as a list comparison, so `when Ports != [22]` and `when Ports != Populated` over `Ports: []` and `Populated: [8080]` open their blocks and `when Ports == [22]` and `when Ports == Populated` leave the rule not applicable, and `when Ports == SecurityGroupIds` over two empty document lists opens its block where `when Ports != SecurityGroupIds` leaves the rule not applicable (the list cases, asserted and under `when`, are pinned by `eval_tests.rs:an_empty_collection_on_the_left_fails_a_comparison (cases "eq_against_an_empty_list_literal_control", "eq_against_a_populated_list_literal", "ne_against_a_populated_list_literal", "eq_against_a_populated_document_list", "ne_against_a_populated_document_list", "eq_against_an_empty_document_list", "ne_against_an_empty_document_list")`, `eval_tests.rs:an_empty_collection_in_a_when_condition_leaves_the_rule_not_applicable (cases "a_populated_list_literal_under_ne_opens_the_gate", "a_populated_list_literal_under_eq_leaves_the_rule_not_applicable", "a_populated_document_list_under_ne_opens_the_gate", "a_populated_document_list_under_eq_leaves_the_rule_not_applicable", "an_empty_document_list_under_eq_opens_the_gate", "an_empty_document_list_under_ne_leaves_the_rule_not_applicable")` and `eval_tests.rs:a_two_list_comparison_fails_on_the_list_mismatch_and_names_no_empty_collection`); in a query filter it deselects the entry. Guard the comparison with `<query> !empty` as a sibling condition where an empty collection is expected and the body should still be checked.

A rule skipped because its condition was decided and simply not met prints no such line, so the message appears only where something needs attention. If you see it, the fix is in the rule or the input rather than in Guard: compare against a value of the same kind, or guard the clause so the mismatch is explicit.

Below are a couple of examples of clauses using binary operators:

- Based on the Template-1 example template:

```
# Checks if BucketName does not contain the string "encrypt" irrespective of casing
Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
```

- Consider the following CloudFormation template:

```yaml
# Template-2
Resources:
  NewVolume:
    Type: AWS::EC2::Volume
    Properties:
      Size: 100
      VolumeType: io1
      Iops: 100
      AvailabilityZone:
        Fn::Select:
          - 0
          - Fn::GetAZs: us-east-1
      Tags:
        - Key: environment
          Value: test
    DeletionPolicy: Snapshot
```

Below are a few Guard clauses based on the above template:

```
# Checks Size of the EC2 volume is within a specific range, 50<= Size <= 200
Resources.NewVolume.Properties.Size IN r[50,200]
```

```
# Checks VolumeType is one of io1, io2 or gp3
Resources.NewVolume.Properties.VolumeType IN [ 'io1','io2','gp3' ]
```

> While these examples illustrate using `S3Bucket`, `NewVolume` in the query, often these are user defined and can be arbitrarily named in an IaC template. To write a rule that is generic and applies to all `AWS::S3::Bucket` resources defined in the template the most common form of query used is `Resources.*[ Type == ‘AWS::S3::Bucket’ ]` to select them. See [Guard: Query and Filtering](QUERY_AND_FILTERING.md) for details on usage and explore the examples directory.

> A filter `[ ... ]` directly after a part that names a collection (a key, `this`, or a `%variable` in a key's place) selects among that collection's entries; directly after a part that names one value (an index, an earlier filter, a `[ keys == ... ]` filter, or a wildcard-expanded member) it tests that value. So `Resources { this[ Type == 'AWS::S3::Bucket' ].Properties.Encrypted == true }` is the same check as `Resources[ Type == 'AWS::S3::Bucket' ].Properties.Encrypted == true` once the block has a value to run over: a block over a null or empty population (a bare `Resources:`, `Resources: {}`, or `Resources: []` under `this[*]`) reads a selection in its body, `this[ f ]`, `this.*[ f ]`, `this[*][ f ]` or `this[*].K[ f ]`, as the empty selection, so it is not applicable as the plain spelling is. The block spelling is also an existence check on `Resources` itself, so over a template with no `Resources` key it fails at its query where the plain spelling is not applicable. A filter predicate written inside such a block tests its entry, not the population: `Resources { this[ this[ Type == 'X' ] !exists ] exists }` reads an entry that is `null` or `{}` exactly as `Resources[ this[ Type == 'X' ] !exists ] exists` does. A bare `this` hands the population on: a block nested in the block, `Resources { this { this[ Type == 'X' ] exists } }`, and a parameterized rule called with it, `Resources { check(this) }` for `rule check(p) { %p[ Type == 'X' ].Properties.Encrypted == true }`, read a bare `Resources:` as `Resources { this[ Type == 'X' ] exists }` and `check(Resources)` do, not applicable rather than failing. The same holds for a wildcard, a key and then a filter at the population: `Resources[*].Properties.Tags[ Key == 'Env' ] exists` and `Statement[*].Condition[ keys == 'x' ] exists` are not applicable over `{}`, over a bare `Resources:` or `Statement:`, over `Resources: {}` and over `Resources: []` alike, where over the bare key and over the empty map they used to fail on the key below it, and their `!exists` over the same two used to pass, reading the key as absent, and is not applicable as well, so a `when` gate written on it that used to open its block leaves it unopened; below the population, `Properties.Statement[*].Condition[ keys == 'x' ]` over a bare `Statement:` still fails on the key `Condition`. Through an alias of the population, `let r = Resources` then `%r.B.Properties.Tags[ Key == 'Env' ] exists`, a template with no `Resources` key fails on the key `B`, as the spelling without the alias does, where the alias used to be not applicable. `Rules[0][ Action == 'allow' ]` is the first rule when its action is `allow`. Inside a block over members, `Rules[*] { this[ Action == 'allow' ] exists }` selects among each rule's own entries, not among the rules; when such a filter selects nothing and its predicate names a key of the member itself, the clause is refused and fails in both polarities. The refusal leads with the spelling that is right where the clause sits, `{ Key == value }` in the block, so `Rules[*] { Action == 'allow' }`, and then names the two spellings that read one member and a list of them alike from outside the block, `X[*] { Key == value }` and `X[*].Key == value`, where `X` is the query that named the member (`Rules` here) and `Key` the key the predicate read (a key-spelled filter, `Rules[ Action == 'allow' ] exists`, is not named: over a `Rules` written as one object it is the same misreading). The same holds when the one map is named by its key: `Resources.B1[ Type == 'AWS::S3::Bucket' ] exists` selects among `B1`'s own entries, and when the filter keeps none of them while `Type` is a key of `B1` and of none of its map-valued entries, it is refused the same way; the predicate is read with a leading `this.` looked through here too, so `Resources.B1[ this.Type == 'AWS::S3::Bucket' ] exists` is refused as the spelling without `this.` is, where it used to be left to evaluate and was not applicable at exit 0; the refusal reads "The filter selected nothing among the map's own entries. `Key` is `Type`, a key of the map itself. Write `X[*] { Key == value }` or `X[*].Key == value`, where `X` is `Resources.B1`, at path /Resources/B1." (the member spellings, `X.*.Key` and `X.* { Key == value }`, are offered as one sentence between the definition of `X` and the path, "For each member's own `Key`: `X.*.Key` or `X.* { Key == value }`.", only when the entry under the key is itself a plain member map, a member named like the key; `B1`'s `Type` is a string, so no member holds it and the sentence is left out, as it is over an intrinsic call such as `Effect: !If [...]` or an empty map such as `B: {}`). Both spellings read one map and a list of them alike, and `X` is the query the author wrote before the filter, so the spellings test the map in hand, `Resources.B1[*] { Type == 'AWS::S3::Bucket' }` or `Resources.B1[*].Type == 'AWS::S3::Bucket'`, and read a `Statement` named the same way whether it is written as one object or as a list; after a key the refusal does not lead with the in-block spelling `Resources.B1 { Type == 'AWS::S3::Bucket' }`, which reads nothing over a list. The spellings carry the placeholders `X` and `Key`, and the query and the key are printed once, so that the console summary and the JSON and YAML reports print the key, both spellings, the definition of `X` and, where a member is named like the key, the member sentence, up to 4096 characters, with a marker where the console cut the explanation there (`-o json` carries the whole text), and the path last; the path, like every part a refusal takes from the template (an entry's or a key's name), is bounded at 256 characters: a name longer than that is cut at its end with a marker naming how much was cut, and a path is cut in its MIDDLE, keeping the top of the document, a marker, its leaf segments and its `[L:x,C:y]` location (the cut is by character count, 128 kept at each end: over a 300-character resource name the path text `/Resources/<name>/Properties/Tags` is 327 characters, 11 + 300 + 16, so a refusal path reads `/Resources/RRRR...[71 more characters cut]...RRRR/Properties/Tags[L:3,C:9]`, the tail being the name's last letters and the leaf segments; the figures are pinned at the boundary lengths, a name of 283 characters left whole and one of 284 cut, a path's text of 286 whole and one of 287 cut, the first length at which the cut shortens a part), and a part only a few characters over the bound is left whole, since the marker would make it longer; each part is bounded as the console prints it, a control or bidirectional character counted as its escape (`\u{202e}`) and a backslash in a quoted key written as `\\` (as every notice writes a key, so a key holding an ESC and a key holding the six characters `\u{1b}` print apart; a backslash in the path stays as written, as on stdout), so a key of three hundred bidirectional overrides prints as at most 256 characters of escapes and a marker; so no template decides the line's length and the sentence around it stays whole. The two collection spellings are the ones that read a map and a list of such maps the same way, which matters where a property may be written as either: an IAM `Statement` written as one object, `PolicyDocument.Statement[ Effect == 'Allow' Action == '*' ] empty`, used to pass by accident and is now refused, and `Statement[*] { Effect == 'Allow' Action != '*' }` or `Statement[*].Action != '*'` reads both shapes. A collection one of whose entries happens to be named like the predicate's key (a parameter called `Type` under `Parameters`) is still a selection among members and is not refused, since its members each carry the key.

#### `IN` against a query

The RHS of `IN` and `NOT IN` can be a query instead of a literal. The rule: a query that **enumerated** a collection while it was resolved (`[*]` or `.*` over a collection, a filter, an interpolated key whose variable enumerated or holds a list of keys, or a variable whose own query did any of those) is the set of its results, and `IN` is membership in that set, exactly as it is in the list literal the results would spell out. A query that **named** one value compares against that value: a list is membership, a string is containment of the LHS string in it. The shape is what the retrieval did, so `Types[*]` over a one-entry list and `Types[0]` are different shapes with the same value.

A scalar on the LHS is a member of the entries with list-valued results flattened one level, whatever part of the query enumerated: a scalar is never a member of a list, so the lists an enumeration hands back can only be lists of candidates for it. A list on the LHS is a subset question: of one result at a time when an earlier part enumerated, of the whole entries when the last part did, exactly as against the written-out list of lists. A value no string entry can be compared with (an int or a `!Ref` map against strings) is refused, and the clause fails in both polarities, as it did before; a value some entry can be compared with is decided, and a value against entries of another non-string kind is a miss, as it is against the written-out list. Under `some`, the verdict is per LHS value in every spelling.

The two polarities for a list on the LHS against list-valued results are deliberately asymmetric and both fail-closed, whichever part enumerated: `IN` is not widened to the pool of all results, and `NOT IN` is not opened by a list that shares one element with a denied one. A result the query cannot resolve, such as `Parameters.*.AllowedValues` over a parameter that has no `AllowedValues`, fails the clause as an unresolved RHS fails any `IN`.

Two sites compare key by key rather than as a set: a map-key filter (`Resources[ keys IN %allowed ]`) and a capture read bare as the RHS (`X IN %name` after `Resources[ name | ... ]`). In a map-key filter a string key is equal to a string element, never contained in it: `[ keys IN ['Environment'] ]` and `[ keys IN 'Environment' ]` both select the key `Environment` and not `Env`. Earlier releases read a bare string, a `let`-bound string or an enumerated string on the right as text the key could be contained in, and a key whose selection moves that way draws a `DEPRECATION` notice; see [KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 13. A negated map-key filter (`NOT IN`, or `!=` over two or more values) selects a key that differs from every right-hand value, where earlier releases selected one that differed from any; a key equal to one of two or more enumerated values, which used to be selected and checked and is left out now (`Resources[ keys NOT IN %exempt ]` over an exemption list of two names, FAIL to PASS or to SKIP), draws its own `DEPRECATION` notice, under the same item. A key or a right-hand value either notice quotes is written as document text is everywhere a notice quotes it: a control, bidi or zero-width character as its Rust escape (`\t`, `\u{200b}`) and a backslash doubled (`a\\b` for the key `a\b`), so the notice stays one line and two keys that differ only in such a character print apart. A map-key filter whose RHS is the empty set is decided by polarity. The empty set is a collection with nothing in it, reached by an enumeration (`keys NOT IN %exempt` with `let exempt = Mappings.Exempt.Names[*]` or `Mappings.Exempt.Names.*` over `Names: []` or `Names: {}`), a key holding null (a bare `Names:` in YAML), or the empty list literal (`let exempt = []`). No key is in it, so `==` and `IN` select no key and the rule reports SKIP; every key is outside it, so `!=` and `NOT IN` select every key and the rule checks all of them. An empty exemption list exempts nothing, where a filter that selected none checked nothing at exit 0. Both engines read it this way. An RHS the key filter cannot resolve fails the filter closed under every comparator, `==` and `!=` included, with a reason naming the path the retrieval stopped at: the keys it would select cannot be decided, so the rule reports a failure rather than selecting none and passing. A right-hand query that is itself refused on the data, `M[ keys == Tags[ Key == 'Env' ].Value ]` or `M[ keys == to_upper(Tags[ Key == 'Env' ].Value) ]` where `Tags` holds a string, fails the filter closed the same way: the map is recorded as undecidable with the refusal as its reason, the clause reads that record as it reads every undecidable map (a rule over the one refused map fails closed in either polarity; under `some` over several maps a sibling whose own selection passes settles the clause past it, so the rule passes; a `when` gate over several maps whose operator is a comparison is settled by a sibling, a decided failure under `all` making the rule not applicable and a pass under `some` opening the block, while a gate under `exists`, `!exists`, `empty` or `!empty` raises on the undecidable map and fails the rule closed whatever the siblings say), and the query goes on to the next map; a capture on the filter holds the marker, so a clause reading it fails closed with the reason. `join` approximates the earlier containment reading where a rule wants it: `Name IN join(Resources.Cfg.Properties.Tags[ Key == 'AllowedNames' ].Value, "|")` folds the results into one string, which `IN` searches as text. #### Filtering through a variable

A filter written after a variable, `%v[ ... ]`, reads the value `v` holds by its shape, classified as the author's `%v[*][ ... ]` classifies it, and parts from `[*]` where the `[*]` rule refuses or enumerates what cfn-guard 3.2.1 decided on the map. Over a list it walks the elements, as `[*]` and the literal path do. Over a map there are six cases. A map with no scalar entry whose own key the predicate does not name is a collection (with one exception below, a map holding one member map that lacks the key an absence predicate names): the entries are walked and those the predicate holds on are kept, the reading the literal path has (`let r = Resources` then `%r[ Type == 'AWS::S3::Bucket' ]` selects what `Resources[ Type == 'AWS::S3::Bucket' ]` selects), and `[*]` walks it the same way. A map with a non-null scalar entry whose keys the predicate does not read as member keys is one object, tested as `[*]` tests it (the table under [one-object-wildcard](#one-object-wildcard) is the rule): the map is selected when the predicate holds on it, and a predicate that compares against keys of which the map holds none, keeps nothing, and is followed by a query part that reads a key the map also lacks (a key, or a second filter whose predicate names only such keys) is refused in both polarities; a bare `empty`, `!empty`, `exists` or `!exists` over the selection is decided by what the map holds, so `%doc[ Foo == 'x' ] empty` over a policy document that lacks `Foo` passes. A map whose entries are all scalars is that case too: `%m[ Status == 'Enabled' ]` with `m` bound to `{ Status: Enabled }` selects the map, as `[*]` and cfn-guard 3.2.1 do (observed on the 3.2.1 binary: `!empty` PASS, `empty` FAIL, a `when` gate on the selection opens), where the literal `Config[ Status == 'Enabled' ]` is refused for naming the map's own key. A map with no scalar entry whose own key the predicate names, none of its map-valued entries holding that key, is one object as well: `let md = Resources.WebServer.Metadata` then `%md[ "AWS::CloudFormation::Authentication" exists ]` over a `Metadata` holding only the authentication and init blocks selects the map, the reading cfn-guard 3.2.1 gave every filter through a variable over one map (observed on its binary: `!empty` PASS, `empty` FAIL, `exists` PASS, a `when` gate on the selection opens and a key read below the selection is decided on the map), where `[*]` runs its own-key enumeration and the literal `Resources.WebServer.Metadata[ ... ]` is refused (item 15 of KNOWN_ISSUES). The same map with a map-valued entry that holds that key too is one object as well: `let md = Resources.Box.Metadata` then `%md[ "AWS::CloudFormation::Authentication" exists ]` over a `Metadata` holding the authentication block beside a `Wrapper` entry that holds one of its own selects the map, so a password check below the selection reads the map's own block (observed on the 3.2.1 binary: `!empty` PASS, the password check FAIL on the map's own block; the negated `!exists` selects nothing, `empty` PASS), where the literal `Resources.Box.Metadata[ ... ]` and `[*]` walk the entries and select `Wrapper` (a key a member holds too is exempt from their own-key refusal, so neither refuses this map, which is why the variable is one object there and not refused). A mixed map, a non-null scalar entry beside a map-valued entry that holds a key the predicate names, is one object as well, the reading cfn-guard 3.2.1 gave every filter through a variable over one map, except where the literal `K[ ... ]` refuses the filter over it: there the variable is refused the same way, since the release's pass over such a map is a silent pass the literal refuses (`%c[ Owner !exists ]` with `let c = Cfg` over `Cfg: { Mode: fast, A: { Owner: o }, B: { Owner: p } }` exits 19 with the sentence `Cfg[ Owner !exists ]` gets, `X` being `%c`; 3.2.1 passed `!empty` over that map, observed on its binary, a check its members fail). Where the literal is not refused the map is tested as one object and the members are not selected in its place: `%p[ Name exists ].Name == 'b'` over `{ Name: a, Inner: { Name: b } }` compares the map's own `a` and fails, as 3.2.1 did (observed on its binary), where the literal `Properties[ Name exists ]` selects `Inner` and passes; `%m[ Metadata."AWS::CloudFormation::Authentication" exists ]` over a resource whose `Wrapper` entry holds that path beside its `Type` string selects nothing, since the resource's own `Metadata` lacks the block (3.2.1: `empty` PASS, a `!exists` below the selection not applicable, observed on its binary), where the literal selects `Wrapper`. `[*]` refuses every mixed map outright. Where the literal is not refused and keeps one or more of the map's entries, the two spellings disagree on what is selected, and the engine writes one `Warning:` line per filter site saying so (the mixed-map warning; a warning and not a `DEPRECATION:` line, since the disagreement is a lasting difference between two spellings and not a reading being retired). A map with no scalar entry whose own key the predicate names is one object as well where that key is the name of one of its members among members sharing a key: `let r = Stack.Resources` then `%r[ BucketA exists ]` over `Stack: { Resources: { BucketA: { Type }, TableC: { Type } } }` selects the `Resources` map (observed on the 3.2.1 binary over the same shape: `!empty` PASS, `empty` FAIL), where `[*]` enumerates the members and selects none and the literal `Stack.Resources[ BucketA exists ]` is refused (item 15 of KNOWN_ISSUES): the one shape where the variable is one object and the literal is refused, which item 11 of KNOWN_ISSUES records. And a map holding one member map that lacks the key an absence predicate (`!exists`, `empty`) names is one object too: a population of one cannot be told from the map by the key the predicate reads, so the walk over the entries keeps the one member for want of the key where the test of the map as one object holds on the map for the same want, the two agree on the entry and differ only in what is selected, and the variable selects the map, as cfn-guard 3.2.1 did: `let md = Resources.Node.Metadata` then `%md[ "AWS::CloudFormation::Authentication" !exists ]` over a `Metadata` holding only an init block selects the map (observed on the 3.2.1 binary: `!empty` PASS, `."AWS::CloudFormation::Init" exists` PASS, `.config exists` FAIL), where the literal and `[*]` select the init block, and `%md[ "AWS::CloudFormation::Authentication" exists ]` over the same map selects nothing under every spelling (3.2.1: `empty` PASS). Every one of these no-scalar one-object readings (a key the map holds alone, a key the map holds beside a member that holds it too, a member named like the key, and the one member map that lacks an absence predicate's key) holds below the top-level sections only and does not apply to a binding of a top-level section, the population alias (`let r = Resources`, `let p = Parameters`, `let m = Mappings`, `let c = Conditions`, and `Outputs`, `Metadata`, `Rules`: the template's seven sections; a `let` of another top-level key, a Kubernetes `spec` or `metadata` at the document root, is not the alias and keeps the readings above): there the walk stays whatever the member count, so `%r[ DeletionPolicy !exists ].Properties.PubliclyAccessible !exists` selects the resource and fails over a template of one resource as over two, `%p[ Type == 'AWS::EC2::KeyPair::KeyName' ].AllowedPattern exists` selects among the parameters though one of them is named `Type`, `%r[ Bucket.Type == 'X' or Properties.Tags empty ]` selects nothing over compliant tagged resources, over a template of one resource as of two, and `%r[ BucketA exists ]` selects none of the members over `{ BucketA: { Type }, TableC: { Type } }`, where `BucketA` is a member's name among members sharing a key, as over `{ BucketA: { Type } }` alone, where it is the map's own key, and is announced by the notice below in both (the predicate holds on the map by the key it names, a pass anchored in the map, so the uniform-population limit does not quiet it). cfn-guard 3.2.1 read the section as one value in each of those (observed on its binary: the first check PASSed with `Properties` not found below `Resources`, the second was SKIP with nothing selected, the third selected `Resources` and failed the gated body on its missing `Type` over one resource as over two, the fourth selected `Resources` over one member as over two (`!empty` PASS, `empty` FAIL); and through `let m = Mappings` over a `Mappings` holding one map, `%m[ Foo !exists ].RegionMap exists` FAILs on the selected map where 3.2.1 PASSed on the section, the same for the other four sections); the walk under the alias is the documented reading of this spelling, the one the notice below was written for, and over a uniform population it is quiet by that notice's listed limit. The cases that part from `[*]` are the ones where the `[*]` rule refuses or enumerates what the released evaluator decided on the map: the all-scalar map under its own key, and below a top-level section the map with no scalar entry that holds a key the predicate names (alone, beside a member that holds it too, or as the name of a member) and the map holding one member map that lacks the key an absence predicate names, and the mixed map.

The reader puts a `[*]` after every `%variable` root that has parts after it. What that `[*]` does depends on what the variable holds.

Over a list, the variable enumerates it: `%r.K` over a list is `Resources[*].K`, with one exception, a filter written directly after the variable over an empty list below the top level, which reads as the literal filter (two paragraphs down). Over `Resources: []` with a filter further along, `%r.B.Properties.Tags[ Key == 'Env' ] exists` is the empty population and is not applicable, as `Resources[*].B.Properties.Tags[ Key == 'Env' ] exists` is; over one element the two spellings pass or are not applicable together; and over `Resources: []` with no filter ahead, `%r.B.Properties.Tags exists` and `Resources[*].B.Properties.Tags exists` both fail on the empty enumeration. The key spelling `Resources.B.Properties.Tags[ Key == 'Env' ] exists` is a different query: a list has no key `B`, so it fails on the key over any list, empty or not. A Terraform plan reads the same way through its alias: `let rc = resource_changes` then `%rc[ type == 'aws_s3_bucket' ].change.after.acl == 'private'` is not applicable over `resource_changes: []`, over a plan with no `resource_changes` key and over a plan whose only change is an instance, as the literal filter spelling is, and passes over a private bucket and fails over a public one as it does; `%rc.change.after.acl == 'private'` over the empty list fails as `resource_changes[*].change.after.acl == 'private'` does.

Over a map, a null or an absent key, the `[*]` the reader adds is not an authored `[*]`: it passes the value on unchanged, so `%r.B` is `Resources.B`, and the alias and key spellings agree. Over `Resources: {}`, a bare `Resources:` and a template with no `Resources` both fail on the key `B`; over a template whose `Resources` map holds `B` with the tag, both pass. The authored `Resources[*].B.Properties.Tags[ Key == 'Env' ] exists` agrees with them over a map that holds `B`, passing, but it reads `Resources: {}`, a bare `Resources:` and a template with no `Resources` as an empty population with a filter ahead and is not applicable there, where the alias and the key read fail on the key.

Below the top level the `[*]` the reader adds after a variable reads an empty list under a filter written directly after the variable as the literal filter does: `let cs = spec.template.spec.containers` then `%cs[ name == 'app' ] exists` over `containers: []` is not applicable, in both polarities and as a `when` gate, as the literal `spec.template.spec.containers[ name == 'app' ] exists` is, where the authored `containers[*][ name == 'app' ] exists` fails on the empty enumeration; `%cs.name` and `%cs[*][ name == 'app' ]` over the same list fail as `containers[*].name` and the authored wildcard do; over a populated list, a missing key or a null the three spellings of the filter, the alias `%cs[ name == 'app' ]`, the literal `containers[ name == 'app' ]` and the authored `containers[*][ name == 'app' ]`, agree (`docs/KNOWN_ISSUES.md`, item 6). The slot reads the list the variable holds however it came to hold it: a let-chain (`let all = spec.template.spec.containers` then `let cs = %all`), a parameterized rule's parameter bound to the list at the call, a key read after the filter (`%cs[ name == 'app' ].image exists`) and a list one level down (`let cs = spec.containers`) read the empty list as the literal filter does. An empty MAP under the same slot reads the same way: `let cs = Resources.X.Properties.Containers` then `%cs[ name == 'app' ] exists` over `Containers: {}` is not applicable in both polarities and as a `when` gate, as the literal `Resources.X.Properties.Containers[ name == 'app' ] exists` is, where it used to fail on the empty enumeration under `exists` and pass on it under `!exists`; the authored `Containers[*][ name == 'app' ]`, `%cs.name`, `%cs[*][ name == 'app' ]` and `%cs.*[ name == 'app' ]` over the empty map keep the enumeration's failure, and over a map with members, a missing key and under a map-key filter (`%cs[ keys == 'x' ]`) the alias and the literal agree as they did. A map-key filter directly after the variable is the slot's own reading, not the literal's: over a populated list `%cs[ keys == 'x' ]` reads as `containers[*][ keys == 'x' ]`, the key filter run over each element, selecting the elements that hold `x` and nothing over a list of maps that lack it; over the empty list it is not applicable (`exists` not applicable, `empty` passes), where both literal spellings fail: the authored `containers[*][ keys == 'x' ]` on the empty enumeration, and `containers[ keys == 'x' ]`, which reads the list as the map to filter, on a type error at any length ("Map Filter for keys was not a struct array"), so that literal's `exists` fails and its `empty` passes over a list. Over a map of containers the slot hands the map on and the two spellings agree.

A parameterized rule's parameter is a variable of the rule, bound at each call, and `%p` anywhere in the rule reads it. A filter capture in the rule's own `when` condition written under a parameter's name, `rule check(p) when Resources[ p | Type exists ] !empty { %p[ Statement exists ] !empty }`, could never be read, so the file is refused when it is loaded, as a name that is both assigned and declared as a filter capture in one scope is; rename the capture.

Inside a block, a `%name` is read in one order by every clause of the block: a key a nested block handed up (`Opts { Allowed[ t | On == true ] !empty }` hands `t` up to the block around it) comes first, then the block's literal `let` of that name, then the enclosing scopes; so a merged key shadows a block's literal `let t = 'x'`, the predicate that reads `%t` compares against the handed-up key, and the shadowing notice asks the author to rename one of the two. (A block that both declares a `let` and captures the same name in its own filter is refused when the file is loaded, so a capture never shadows a `let`.) The rows are pinned by `eval_tests.rs:a_merged_key_shadowing_a_blocks_let_writes_no_quiet_record_at_either_site`.

When the variable holds a single map with no scalar entry, what the predicate names decides. Below the top-level sections (under the population alias the map is walked instead, as the item above says), a predicate naming a key the map holds itself, whether none of its map-valued entries holds that key or one does, is asked of the map, which is selected when it holds: `let md = Resources.WebServer.Metadata` then `%md[ "AWS::CloudFormation::Authentication" exists ]` selects the `Metadata` map, and over a `Metadata` that also holds a `Wrapper` entry with an authentication block of its own it still selects the map, so what a rule reads below the selection is the map's own block, never `Wrapper`'s. A predicate naming no key the map holds is tested against each entry, the entries being that map's own values, and a positive predicate such as `testBasic exists` holds on an entry only when that entry is itself a map carrying that key. A resource holds a `Type` string, a scalar entry, so it is one object and the predicate is tested on it, as `Resources.WebServer[*][ ... ]` tests it. Over a collection, a map with no scalar entry whose own key the predicate does not name, this spelling and the literal `X[ ... ]` agree: an entry the predicate holds on is selected in the map's place and an entry it rejects is not. Over a map with a scalar entry the variable spelling agrees with `[*]` instead and tests the map as one object, so `%auth` above selects the resource (the alias and the literal part on a map that holds scalars beside sub-maps under an absence predicate: `let s = spec` with `%s[ securityContext !exists ] !empty` opens its gate on a Deployment `spec` whose `replicas: 3` sits beside its sub-maps, read as one object, and fails a `spec` with no `securityContext` in the body, while the literal `spec[ securityContext !exists ] !empty` is refused there, fail closed, since the predicate holds on the `spec` itself and the sub-maps it kept beside the scalar it passed over may be the fields of one object, which the refusal says and remedies: `spec[*][ securityContext !exists ]` to read the spec as one object, the one spelling it names there since no sub-map holds `securityContext` and `spec.*[ securityContext !exists ]` would keep the same sub-maps again (where a sub-map does hold the key it names `spec.*[ ... ]` for the members and `spec.securityContext !exists` for the map itself instead); `.*` reads the members under every map, and over a map with no member its empty answer is the members reading, not a verdict lost). A predicate about the value itself, `Labels[ k | this == 'prod' ]`, still tests a scalar entry and binds its key. A map whose entries are all scalars under a predicate that names a key the map itself holds is one object through the variable, as under `[*]`: `%m[ Status == 'Enabled' ]` with `m` bound to `{ Status: Enabled }` selects the map and `%m[ Status == 'Enabled' ].Status == 'x'` fails on the comparison (cfn-guard 3.2.1 gives the same, observed on its binary), where the literal `Config[ Status == 'Enabled' ]` is refused, naming the key. What a rule over the selection reports depends on what was selected. **Behavior change in 3.2: a filter after a key over a map with a scalar entry.** Earlier versions handed every entry of the map to the predicate, scalars included, so over an all-scalar `Properties` the clause `Resources.B.Properties[ Foo !exists ] !empty` selected every property by the absence of `Foo` and passed, and `when Resources.B.Properties[ Foo !exists ] !empty { ... }` opened its block.
Since 3.2 a predicate about keys passes a non-null scalar entry over, under the literal `Key[ ... ]`, under `.*`, and under a variable bound to a mixed map, a scalar beside sub-maps that hold a key the predicate names (`[*]`, and a variable bound to a map with a scalar entry whose keys the predicate does not read as member keys, read such a map as one object instead; a variable bound to a map with no scalar entry has nothing to pass over); over the all-scalar `Properties` the filter passes every property over, keeps nothing, and the predicate holds on `Properties` itself by the absence of `Foo`, so it is refused in both polarities, defining `X` and naming the `X[*][ ... ]` remedy (`X.*[ ... ]` for the members and `X.Key !exists` or `X.Key empty`, the predicate's own absence operator, for the map itself where a map-valued entry was rejected, or kept while some sub-map, the kept one included, holds a key the predicate names): `!empty` and `empty` fail, and the `when` gate fails rather than opening or skipping.
A predicate that compares the entry itself (a bare `this` under any operator: `this == 'prod'`, `this !empty`, `this exists`, alone or beside a clause that names a key; `this !empty` and `this exists` count only as the whole predicate or an `or` arm of it) still tests the scalar, so `labels[ this !empty or env exists ] empty` over `labels: { team: '', tier: web }` keeps `web` as `labels[ this !empty ] empty` does, and adding a disjunct never makes a filter select less (after a key or a `%name` only: under `.*` and `[*]`, a walk over members, a bare `this` that asks no more than `exists` or `empty` leaves a scalar entry passed over and an all-scalar map enumerated when the predicate names a key the map lacks, so `Resources.*.Properties.*[ "Fn::ImportValue" exists or this empty ] empty` reads as `Properties.*[ "Fn::ImportValue" exists ] empty` does over an SQS queue: passing a queue of scalar properties, passing one with a map-valued `RedrivePolicy` beside an int, failing one whose `QueueName` imports a value); a scalar so handed on and kept THROUGH a key absence it holds vacuously (`Properties[ Foo !exists or this !empty ] !empty` over an all-scalar `Properties`: `Foo !exists` holds on a string for want of any key, so every property was selected and `!empty` passed, the pre-3.2 reading back through the `this` hand-off) is refused in both polarities, WHATEVER the `this` clause beside the absence is and whatever it decided: an `or` arm (`Foo !exists or this == 'b'` selects exactly what `Properties[ Foo !exists ]` selects, since the absence arm keeps every scalar by itself), a comparing conjunct that rejects some scalars and keeps others (`Foo !exists  this == 'b'` over `{ BucketName: b, Region: us-east-1 }`, `this empty  env !exists`), one every scalar satisfies (`this != ''`, `this is_string`, `this != 'slow'  Owner !exists` over `{ Mode: fast }`; a `Tier: web` beside `Mode` changes nothing), a negated type test a map satisfies too (`this !is_list`, `this !is_int`, `this !is_string` over a mixed map: one reading passed these because it asked the map read as one object, whose answer to a bare `this` the predicate's shape fixes), an `or` of `this` comparisons or of a `this` clause with a key clause (`Foo !exists  this == 'b' or Bar exists`), and a `Properties` that holds the very `Foo` the absence clause names; the one sentence names the absence clause and the first property the filter kept, claims nothing about what the `this` clause decided, and its remedy asks the two questions apart: `X.Key !exists` for the map itself and `X[ ... ]` with the absence clause left out for the entries (`X.*[ ... ]` too where the map holds a member; beside a sub-map that holds a key the predicate names, `X.*[ ... ]` with the `this` clause left out reads the members), never `X[*][ ... ]`, which over a map of scalars reads one object and passes on every template; a `this !empty` or `this exists` conjunct beside other clauses (or the same by `not`: `not this empty`, `not this !exists`) hands no scalar over, since it decides nothing a non-empty scalar fails, while `this empty` and `this !exists` fail every non-empty scalar and are handed over as `this == 'x'` is, so `Properties[ this !empty  Foo !exists ] !empty` is refused as `Properties[ Foo !exists ] !empty` is, and `Properties[ Foo !exists  this != '' ] !empty` over the same all-string properties is refused with it; a predicate whose only absence-shaped clause is a bare `this empty` (`labels[ this empty ]`) tests each string's own value, keeps nothing vacuously and is decided for real; an all-scalar map under a predicate that names one of its own keys is refused, as before; and a null entry, a bare key, is handed to the predicate under every spelling.
A rule that asked the map about its own key through its entries, `Properties[ Foo !exists ]`, is written `Properties.Foo !exists`.

When the filter did not select the map it used to select -- the map is a collection to the slot (no scalar entry: a resource, which holds a `Type` string, is one object and is never announced, so this notice reaches `let b = Resources.<Id>` only over a map written without `Type`), the predicate holds on it, in a way the rule relied on (a key the predicate names was found on the map, even when a filter or wildcard after it selected nothing, as in `Properties.Tags[ Key == 'Owner' ] empty` on a bucket with no Owner tag, or a lookup got into the map before the key it names was missing, as in `Properties.BucketEncryption !exists` on a bucket whose `Properties` has no `BucketEncryption`; a pass that found nothing of the map is announced or not as "When the notice stays quiet" below says), and the map is not among what the filter selected -- Guard writes a `DEPRECATION` notice to stderr naming the `let` (or the parameter and its rule) and the filter as written, the map that lost its selection and how many of its entries were selected in its place, the filter's position and the two rewrites. The verdict does not move. A `let` bound to a function call (`let doc = json_parse(...)`), a `let` bound to a map written out in the rules file, and a parameter bound to either at its call site (`check(json_parse(...))`) lose a selection the same way, when the map they hold is a collection (a parsed policy whose entries all carry `Sid` under `%doc[ Sid !exists ]`; a parsed policy with a `Version` string beside its `Statement` list is one object and loses nothing), and are announced the same way, with the differences their binding makes: the call is printed as written and the literal is elided to `let policy = { ... }`; a parsed map is named by the property it was parsed from and a literal map by no path, since the document holds neither; and the second rewrite is to filter a collection the map holds (`%doc.<key>[ ... ]`), since there is no parent path to bind. One line per filter, however many maps the variable holds and however many test cases evaluate the file, and one per filter site across the data files of one `validate` run, with the `NOTE:` trailer for a site later files also drew; how the line and the trailer are written is described once, under [How `validate` writes notices](#notices). A binding that projects, such as `Resources.*[ ... ]`, is announced when its filter walked the selected values' entries -- the author's own `[*]` before the filter, or a key after the projection as in `Wrapper.*[ Marker == 'x' ].Config` and `Resources.*[ Type exists ].Properties` -- because the old reading selected each map it held the same way; `%b[ ... ]` straight after a projection still tests each selected value as a whole and is not announced.

##### When the notice stays quiet

The notice is for a selection a rule relied on. It is not raised:

- when the predicate does not hold on the map and the map is a collection, or an object over whose fields the filter selects nothing: the previous reading selected nothing there either, as for `let r = Resources` filtered for a `Type` the template lacks (the resources share `Type`, a collection), or `let d = Resources.LT.Properties.LaunchTemplateData` with `%d[ ImageId == 'ami-1' ]` over sub-maps none of which holds `ImageId`. No shape moves here through the variable: a map with no scalar entry that carries the checked key is one object to the slot except under the population alias (the alias exception above), whether a sub-map holds the key too or none does, so `let s = spec` with `%s[ securityContext !exists ]` over a `spec` of `selector`, `template` and a `securityContext` sub-map, with no scalar beside them, does not hold, selects nothing, passes `empty` and leaves a `when ... !empty` gate `SKIP`, as the previous release did, quietly; an object with a scalar entry is tested as one object and selects nothing there, quietly, too. The author's `%s[*][ securityContext !exists ]` over that `spec` with a `template` that holds a `securityContext` of its own walks it (a key a field holds too is exempt from the own-key refusal) and selects `selector` and the `securityContext` sub-map itself, each lacking a `securityContext` of their own, so `empty` fails where the previous reading passed it: that selection gained over an object's fields is announced, naming the selection gained, the map and the binding, with the same two rewrites. It goes out only for a selection held by absence, every selected field lacking the key; a positive predicate that selects the entry carrying what it asks for (`let m = Resources.Only` with `%m[ Metadata."AWS::CloudFormation::Authentication" exists ]` over a map with no scalar entry and no `Metadata` of its own, selecting the `Wrapper` entry that holds the path) is the reading described above and is not announced (the same resource with a `Type` string beside `Wrapper` is a mixed map, and the same resource with a `Metadata` of its own beside `Wrapper` holds the predicate's key: each is tested as one object, nothing is selected, as 3.2.1 read it);
- when the predicate held on the map only because a key it names is missing from the map (`empty` or `not exists` over a key the map does not have) and the map is a collection of items the predicate is about, which Guard reads from the entries themselves: every entry is itself a map on which the predicate held, through a key the entry carries or for want of the key. `let r = Resources` with `%r[ Properties.Tags empty ]` over untagged buckets is this case. `Resources` has no `Properties`, every resource under it does and lacks `Tags` beneath it, the author meant the resources, and the earlier reading's selection of the whole `Resources` map failed compliant templates for nothing; a notice there would tell authors to rewrite a rule written the way this document recommends. Under the population alias -- `let r = Resources`, an alias of it (`let all = Resources` then `let r = %all`), or a parameter passed either -- an entry that carries the key and fails the check is still a member too: `%r[ DeletionPolicy !exists ]` over resources none of which carries the key (the check holds on each) and over resources one of which does (found there, holds elsewhere) is quiet either way, and so is the idiom over a compliant, tagged template; a populated template does not flip the notice. Under a variable the author named -- `let p = Resources.LT.Properties`, a nested collection such as `let r = Template.Resources`, a parameter bound to either -- an entry the predicate held on is a member, and a sub-map that carries the very key the author checked absent makes the map an object: the lost selection is announced. `let p = Resources.LT.Properties` with `%p[ TagSpecifications !exists ]` over a `Properties` holding only a `LaunchTemplateData` sub-map that carries the key, the notice's own example, used to open its `when ... !empty` gate and fail on a missing `LaunchTemplateName` (cfn-guard 3.2.1 tested the bound map as one value, observed on its binary: the gate opened and the guarded rule failed on the missing name) and is now `SKIP`, announced; a `Properties` that also carries a scalar `LaunchTemplateName` beside that sub-map is a mixed map, a scalar beside a member that holds the checked key, and the filter is refused in both polarities as the literal `Properties[ TagSpecifications !exists ]` is, FAIL at exit 19 (observed on `tag_specifications_absent_gate_through_a_variable.guard` over `launch_template_with_tag_specifications.yaml`; cfn-guard 3.2.1 read that map as one value too, opened the gate and passed, observed on its binary); and the assertion form over all-scalar properties lacking the key, `%p[ Tags !exists ] !empty` over `{ BucketName: b }`, passes at exit 0, the map selected by the absence (observed on `tags_absent_not_empty_through_a_variable_bound_to_properties.guard` over `scalar_properties_without_tags.yaml`). Two or more sub-maps are a collection only when they are the same kind of thing, which Guard reads as a key name every one of them carries (`Type` on the resources of a template, a `Config` on each of a map of configs); sub-maps that share no key name are the fields of an object, and an absence check that holds on each of them for want of the key is a check about the object: `let d = Resources.LT.Properties.LaunchTemplateData` with `%d[ MetadataOptions !exists ]` over `Monitoring` (`Enabled`) and `IamInstanceProfile` (`Name`) sub-maps is announced, as is `let s = spec` with `%s[ securityContext !exists ]` over a Kubernetes Deployment `spec` of `selector` and `template` (the same `spec` carrying a `securityContext` sub-map is the gained selection of the first bullet, announced from the other direction). A map of sub-maps that lack the checked key and share some other key still reads as a collection, and [KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 11 records that limit. The same rule reads a nested collection, and that is a listed limit of this notice ([KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 11): `let r = Template.Resources` with `%r[ Properties.Tags empty ]` over a nested template whose buckets carry `Tags`, or with `%r[ DeletionPolicy !exists ]` over one whose resource carries the key, draws the notice although the author meant the resources, while the same rules file over a nested template whose resources lack the key is quiet, so the template decides the notice there. Guard reads the entries and the binding's shape and cannot tell a nested collection from an object of sub-maps by them; the alternative, reading entries that all carry a scalar `Type` as a population whatever bound the map, which would quiet nested templates and still announce the launch-template example, is not built, because the notice is a deprecation line at exit 0 and the verdict does not move with it. (An earlier reading counted a sub-map the predicate reached into as a member whatever bound the map, which kept the launch-template example above quiet while its gate closed.) A null entry, such as a bare `Placeholder:` resource with no body, is a member with nothing to read and is passed over: it neither makes the collection an object nor keeps the notice quiet on its own; an empty-map entry, `Placeholder: {}`, is the same empty resource spelled the JSON way and is passed over the same way, by the shared-key test as by the entry reading, so the idiom is quiet over either spelling. An entry under an intrinsic directive key beside the resources, any key with the `Fn::` prefix (`'Fn::Transform': { Name: 'AWS::Include', Parameters: { ... } }`, the common one; under `AWS::LanguageExtensions` a list-valued `'Fn::ForEach::Buckets': [ ... ]`; a map-valued `Fn::ImportValue` written where a member would be), is an instruction to the service, not a member: every reading of the map's entries passes it over, the shared-key test, the object-of-fields test and the per-entry probe alike, so a template that includes a snippet or loops over a list this way keeps the idiom quiet, where the transform's `Name` and `Parameters` keys would otherwise have read as a field sharing nothing with the resources, and the ForEach list as a scalar field, and announced the notice over a compliant template. The rule is the prefix, not the one name; matching `Fn::Transform` alone would read a map with any other `Fn::` key beside its members as an object, and [KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 11 records that alternative. An empty map, or a map whose entries are all null or all empty maps (`Properties: {A: {}, B: {}}`, the JSON spelling of `A:` and `B:`), has no entry to read, and there the binding decides: `Resources: {}` is quiet, with nothing to lose, through any variable that names a top-level key (directly, through an alias chain or a parameter), while an empty map the author named is announced, as `let p = Resources.Q.Properties` with `%p[ KmsMasterKeyId !exists ]` over `Properties: {}` is, because the earlier reading selected the map and a `when` over the selection ran, where the selection is now empty and the rule is `SKIP`. An empty map, or one whose entries are all null or all empty maps, carries nothing Guard could read a population from, so that rule has two shapes it cannot tell apart, both listed in [KNOWN_ISSUES.md](KNOWN_ISSUES.md) item 11: an empty top-level object such as a Kubernetes `metadata: {}` under `let md = metadata` names a top-level key and stays quiet although a `when` gate over `%md[ labels !exists ]` closed where it used to open (a populated `metadata` of scalars is one object and is tested as such), and an empty nested collection, `let r = Template.Resources` over `Template.Resources: {}`, is announced although the same rule over a nested collection whose entries hold the check through a key they carry is quiet. The same pass on a map that is not such a collection and has no scalar entry -- an entry the predicate never reached into -- is a check the author wrote about the map itself under any binding, the earlier reading's selection of it was one the rule relied on, and it is announced: `let p = Resources.LT.Properties` with `%p[ TagSpecifications !exists ]` over a `Properties` holding only the `LaunchTemplateData` sub-map. A map with a scalar entry whose keys the predicate does not read as member keys is tested as one object instead, so `let md = metadata` with `%md[ labels !exists ]` on a Kubernetes `metadata` map of scalars and `let p = Resources.Bucket.Properties` with `%p[ Tags !exists ]` on a properties map of scalars each select the map itself by the absence, as `[*]` does, and nothing is announced; where the scalar sits beside a sub-map that carries the checked key (`%p[ TagSpecifications !exists ]` over `LaunchTemplateName: x` beside the `LaunchTemplateData` that holds `TagSpecifications`) the map is mixed and the filter is refused, as above, with no notice either. In a disjunction the question is asked of the clause that passed: in `%r[ Bucket.Type == 'X' or Properties.Tags empty ]` the failing `Bucket.Type` clause does not count, although it found a key of `Resources`;
- when the predicate, or a `when` block or nested block inside it, names another rule or a variable, declares a `let` of its own, or compares against a function call: such a predicate cannot be re-run quietly, so it is not probed and a lost selection there goes unannounced. A `when` block or nested block whose clauses do none of these is probed like a bare clause, and a `when` block whose condition does not hold on the map neither holds nor fails the predicate, as it neither holds nor fails the filter;
- when the filter is on a literal path, or when the variable holds a list: neither lost a selection.

**Behavior change in 3.2: a variable bound to another variable that names a top-level key.** `let all = Resources` then `let r = %all` is read as `Resources` wherever `%r` is used, as a parameter passed `%all` already was. A filter or `.*` over `%r` on a template with no `Resources` key, or an empty one, is an empty selection and the clause is not applicable, as it is for `let r = Resources` and for `Resources` written out; earlier versions failed such a clause through the alias (`%r.*[ Type == 'AWS::S3::Bucket' ].Properties.BucketName == 'b'` exited 19 over `{}` and over `Resources: {}`) and passed a `!exists` or `empty` assertion over the same selection, where both are now not applicable. The direct spelling did not move. No notice marks this move: a document with no resources holds no map a filter could lose.

To test the map, move the predicate into the `when` condition:

```
let m = Resources.WebServer
rule authentication_has_no_password when %m.Metadata."AWS::CloudFormation::Authentication" exists {
    %m.Metadata."AWS::CloudFormation::Authentication".*.password !exists
}
```

To select from a collection, bind one and filter that:

```
let auth = Resources.*[ Metadata."AWS::CloudFormation::Authentication" exists ]
rule authentication_has_no_password when %auth !empty {
    %auth.Metadata."AWS::CloudFormation::Authentication".*.password !exists
}
```

Both fail on an instance whose authentication block holds a `password`, and neither raises the notice. They are not interchangeable: the first checks only the instance it names, passing while a launch configuration beside it holds a password, and is `SKIP` on a template that has no `WebServer`; the second checks every resource that carries the block, whatever its type or logical id, failing on that launch configuration and passing on a template whose blocks hold no password.

#### Comparing against a query that resolves to no values

When the RHS of a binary operator is a query, it can resolve to no values at all. This usually happens because the query selects a resource type that the input does not contain:

```
# %denied is empty for any template that defines no KMS keys
let denied = Resources.*[ Type == 'AWS::KMS::Key' ].Properties.KeyId

rule bucket_name_is_not_denied {
    Resources.*[ Type == 'AWS::S3::Bucket' ].Properties.BucketName != %denied
}
```

There is nothing to compare the LHS against, so the clause cannot be decided and it `FAIL`s. This applies to both polarities: `IN %denied` and `!= %denied` both fail when `%denied` resolves to no values. The failure message says that the reference resolved to no values, so the fault is not mistaken for one in the input.

Failing here is deliberate, and it is a change from earlier versions, which reported `SKIP`. A `SKIP` exits `0` and is indistinguishable from a `PASS` at a CI gate, so the rule above reported success for every template while comparing nothing, including a template whose bucket name was on the denylist that the query failed to populate.

If a query is expected to resolve to no values, state that with a `when` guard. The condition fails, so the rule does not apply and is reported as `SKIP`:

```
rule bucket_name_is_not_denied when %denied !empty {
    Resources.*[ Type == 'AWS::S3::Bucket' ].Properties.BucketName != %denied
}
```

This is the same `when %query !empty` idiom used to scope a rule to templates that contain the resources it checks. A comparison written directly as a `when` condition is also reported as `SKIP` rather than `FAIL` when its reference is empty, because a failing condition would drop the block it guards.

A right-hand query that stops at a key the document lacks (`Parameters.Missing.Default` over a template with no `Parameters`) is a value the document lacks rather than a query with no values, and a comparison against it is a decided failure for each left-hand value, under every comparator and in both polarities, with the path the retrieval stopped at as the reason. `some` changes nothing here: with no left-hand value that passed, `some Resources.*.Properties.Name != Parameters.Missing.Default` fails as an assertion, reports its rule not applicable as a `when` condition, and deselects every entry as a filter predicate. The escape hatch is the one above, spelled for the reference: `when Parameters.Missing.Default exists { ... }`. With a left-hand value that passed against a resolved right-hand value beside the absence, `some` passes on that pair while the `match_all` spelling is not applicable (`some Port != <selection>` over `Port: 22`, one resource whose selection is absent and one whose selection holds `80`): one left-hand value, two statuses, and the quantifiers read them differently. ## <a name="notices"></a> How `validate` writes notices

A `DEPRECATION:` notice on stderr, about a reading that changes in a later release or that this release has replaced for a shape the notice names (the list-twin notice: the one-object reading of a pair-shaped filter over a map of scalars is retired, and the twin's verdict stands), describes the rule, not one evaluation of it, so `validate` writes each once per run. The line about a `let` read behind a chain of more than 16 `let`s (KNOWN_ISSUES.md, "Runtime notices carry no provenance") is written on this channel too though nothing is deprecated, because the once-per-run channel is the one the engine has for a notice about the rules file as written; a channel of its own would be a new line shape on stderr, a contract change left for a later release. The one exception is the moved-reading `Warning:` line about a key filter's function argument (see FUNCTIONS.md), which is kept per data file: each data file whose reading moved gets its own line beside its own report, naming that file, and the trailer described below never names a file for it. The other `Warning:` lines, about a condition the run went on from, are written where the condition is met. ## Custom Message

You can add a custom message to a clause. A custom message is added at the end of a clause as follows:

```
  <query> <operator> [query|value literal] [custom message]
```

`custom message` is expressed as `<<message>>` where message is any string which ideally provides information regarding the clause preceding it. This message is displayed in the verbose outputs of the validate (provide links) and test (provide links) commands and can be used to supply information helpful for understanding/debugging rules file evaluation on hierarchical data. The Template-2 example template clauses with custom message will look as follows:

```
Resources.NewVolume.Properties.Size IN r[50,200]
<<
    EC2Volume size must be between 50 and 200,
    not including 50 and 200
>>
Resources.NewVolume.Properties.VolumeType IN [ 'io1','io2','gp3' ] <<Allowed Volume Types are io1, io2, and gp3>>
```

A message written across several lines ends at the first later line that starts with `>>` (leading whitespace aside); whatever follows that `>>` on the same line is read as rule text, so a message body line may not itself start with `>>`. A message body may not contain `<<`; see [Known Issues](KNOWN_ISSUES.md) for what that excludes.

### Combining Clauses

Now that we have a complete picture of what constitutes a clause, let us learn to combine clauses. In Guard, each clause written on a new line is combined implicitly with the next clause using conjunction (boolean `and` logic):

```
# clause_A ^ clause_B ^ clause_C
clause_A
clause_B
clause_C
```

You can also combine a clause with the next clause using disjunction by specifying `or|OR` at the end of the first clause.

```
  <query> <operator> [query|value literal] [custom message] [or|OR]
```

Disjunctions are evaluated first followed by conjunctions, and hence Guard rules can be defined as a conjunction of disjunction of clauses that evaluate to a `true` (`PASS`) / `false` (`FAIL`). This can be best explained with a few examples:

```
# (clause_E v clause_F) ^ clause_G
clause_E OR clause_F
clause_G

# (clause_H v clause_I) ^ (clause_J v clause_K)
clause_H OR
clause_I
clause_J OR
clause_K

# (clause_L v clause_M v clause_N) ^ clause_O
clause_L OR
clause_M OR
clause_N
clause_O
```

This is similar to the [Conjunctive Normal Form (CNF)](https://en.wikipedia.org/wiki/Conjunctive_normal_form).

All clauses written based on the Template-1 example template can be combined as follows:

```
Resources.S3Bucket.Properties.BucketName is_string
Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
Resources.S3Bucket.Properties.BucketEncryption exists
Resources.S3Bucket.Properties.BucketEncryption is_struct
Resources.S3Bucket.Properties.Tags is_list
Resources.S3Bucket.Properties.Tags !empty
```

All clauses above are combined using conjunction. As you can see, there is repetition of part of the query expression in every clause. You can improve composability and remove verbosity and repetition from a set of related clauses with the same initial query path using a query block.

## Blocks

### Query blocks

The above set of clauses can be written in block format as follows:

```
Resources.S3Bucket.Properties {
    BucketName is_string
    BucketName != /(?i)encrypt/
    BucketEncryption exists
    BucketEncryption is_struct
    Tags is_list
    Tags !empty
}
```

The above composition is referred to as query blocks as the query preceding the block sets the context for clauses inside the block. This improves composability and removes verbosity and repetition while writing multiple related clauses with the same initial query path.

### When blocks - When condition for conditional evaluation

Blocks can be evaluated conditionally using `when` blocks; `when` blocks take the following form:

```
  when <condition> {
      Guard_rule_1
      Guard_rule_2
      ...
  }
```

- The `when` keyword designates the start of the when block.

- `condition` can be any Guard rule. The block is evaluated only if the evaluation of the condition results in `true` (`PASS`).

Below is an example using the Template-1 example template:

```
when Resources.S3Bucket.Properties.BucketName is_string {
    Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
}
```

The clause within the when block will only execute if `BucketName` is a string. If the value for `BucketName` was being referenced from a Parameter as shown below, the clause within the when block will not be executed.

```
Parameters:
  S3BucketName:
    Type: String

Resources:
  S3Bucket:
    Type: "AWS::S3::Bucket"
    Properties:
      BucketName:
        Ref: S3BucketName
    ...
```

### Named rule blocks

Named rule blocks allow for re-usability, improved composition and remove verbosity and repetition. They take the following form:

```
  rule <rule name> [when <condition>] {
      Guard_rule_1
      Guard_rule_2
      ...
  }
```

- The `rule` keyword designates the start of a named rule block.

- `rule name` can be any string that is human-readable and ideally should uniquely identify a named rule block. It can be thought of as a label to the set of Guard rules it encapsulates where Guard rules is an umbrella term for clauses, query blocks, when blocks and named rule blocks. The `rule name` can be used to refer to the evaluation result of the set of Guard rules it encapsulates, this is what makes named rule blocks re-usable. It also helps provide context in the validate (provide links) and test (provide links) command output as to what exactly failed. The `rule name` is displayed along with it block’s evaluation status - `PASS`, `FAIL`, or `SKIP`, in the evaluation output of the rules file:

```
# Sample output of an evaluation where check1, check2, and check3 are rule names.
_Summary__ __Report_ Overall File Status = **FAIL**
**PASS/****SKIP** **rules**
check1 **SKIP**
check2 **PASS**
**FAILED rules**
check3 **FAIL**
```

- Named rule blocks can also be evaluated conditionally by specifying the `when` keyword followed with a `condition` after the `rule name`.

Reiterating the `when` block example below:

```
rule checkBucketNameStringValue when Resources.S3Bucket.Properties.BucketName is_string {
    Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
}

# The above can also be written as follows
rule checkBucketNameIsString {
    Resources.S3Bucket.Properties.BucketName is_string
}
rule checkBucketNameStringValue when checkBucketNameIsString {
    Resources.S3Bucket.Properties.BucketName != /(?i)encrypt/
}
```

Named rule blocks can be re-used and grouped together with other Guard rules. Below are a few examples:

```
rule rule_name_A {
    Guard_rule_1 OR
    Guard_rule_2
    ...
}

rule rule_name_B {
    Guard_rule_3
    Guard_rule_4
    ...
}

rule rule_name_C {
    rule_name_A OR rule_name_B
}

rule rule_name_D {
    rule_name_A
    rule_name_B
}

rule rule_name_E when rule_name_D {
    Guard_rule_5
    Guard_rule_6
    ...
}
```

The above styles of compositions will be discussed in-depth in the [Guard: Complex Composition](COMPLEX_COMPOSITION.md) document.
